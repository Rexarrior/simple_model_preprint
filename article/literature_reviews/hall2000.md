## Вопрос и вклад статьи

Hall, Potts, and Sriskandarajah исследуют статическое детерминированное расписание заданного множества работ на нескольких одинаковых параллельных машинах, когда каждой работе перед processing требуется setup, выполняемый одним общим server. Главная цель статьи — построить карту вычислительной сложности для нескольких классических objectives и разных ограничений на setup и processing times (PDF 1–3 / печ. 223–225).

Авторы ставят для каждого варианта один из двух типов вопросов:

1. существует ли polynomial- или pseudo-polynomial-time exact algorithm;
2. если такой алгоритм маловероятен, является ли recognition version binary или unary NP-complete.

Вклад не сводится к makespan. Статья систематически рассматривает `C_max`, `L_max`, суммарное и взвешенное completion time, число и вес late jobs, суммарную и взвешенную tardiness. Для unit processing times авторы устанавливают эквивалентности с классическими single-machine problems; для остальных вариантов дают специальные algorithms или hardness reductions (PDF 3–6 / печ. 225–228).

Для нашей статьи особенно важны четыре результата источника:

- common server является явным capacity-1 resource, операции которого входят в допустимое расписание;
- server operation имеет конкретное место: setup/loading выполняется перед processing соответствующей работы;
- занятость server может оставлять параллельные машины без работы, поэтому одной балансировки machine workload недостаточно;
- даже при простых setup times сложность makespan-задачи быстро меняется от точной разрешимости к NP-completeness.

## Постановка и метод

### Ресурсы, работы и временная структура

Базовая среда задаётся так (PDF 1, 3 / печ. 223, 225):

- имеются `m` одинаковых параллельных машин `M_i` и `n` заданных работ `N={1,...,n}`;
- каждая работа `j` должна быть nonpreemptively обработана ровно на одной машине;
- processing time работы равно `p_j`;
- до processing единственный общий server выполняет setup/loading длительности `s_j` на выбранной машине;
- setup и processing не прерываются;
- setup не может выполняться на машине, пока эта машина обрабатывает работу;
- после завершения setup машина обрабатывает работу без участия server, а server может обслуживать другую машину;
- одновременные запросы машин к server неизбежно создают machine idle time;
- `p_j` и `s_j` целочисленны; в algorithms предполагается `p_j>=1`, `s_j>=1`, а некоторые hardness proofs допускают `p_j=0` только для упрощения изложения и отмечают возможность rescaling;
- release dates, precedence constraints между различными работами, неодинаковые машины и preemption в постановку не включены.

Критически важно точное положение server operation. Источник моделирует цепочку

```text
common-server setup/loading -> machine processing.
```

Setup требует одновременно свободных server и целевой машины. Processing затем занимает машину, но не server. Отдельной server operation после processing — unloading, inspection, acceptance или verification — в модели нет. Повторных циклов `processing -> review -> rework` также нет.

Источник прямо указывает, что server может быть human operator, robot, automated guided vehicle или иное оборудование (PDF 2 / печ. 224). Это прямой результат о допустимой физической природе server. Однако интерпретация именно как разработчика, который формулирует спецификацию и проверяет код, остаётся нашей структурной аналогией.

### Нотация и objectives

Авторы расширяют стандартную классификацию `alpha|beta|gamma`, добавляя server `S` в первое поле (PDF 3–4 / печ. 225–226):

- `Pm;S` — фиксированное число `m` одинаковых параллельных машин и один server;
- `P;S` — число машин произвольно;
- `p_j=1`, `s_j=1`, `s_j=s` фиксируют специальные случаи;
- отсутствие такого ограничения означает arbitrary processing или setup times.

Рассматриваются objectives (PDF 4 / печ. 226):

- makespan `C_max=max_j C_j`;
- maximum lateness `L_max=max_j(C_j-d_j)`;
- `sum C_j` и `sum w_j C_j`;
- `sum U_j` и `sum w_j U_j`;
- `sum T_j` и `sum w_j T_j`.

Для M0–M4 прямым совпадением objective является только `C_max`: время завершения фиксированного набора работ. Остальные criteria показывают широту source model, но не входят в текущую статью.

### Active и list schedules

Расписание называется active, если при фиксированной последовательности нельзя уменьшить completion time одной работы, не увеличив completion time другой. Generic Algorithm List сначала задаёт последовательность `sigma`, затем по очереди помещает каждую работу на первую освободившуюся машину; setup начинается при одновременной доступности машины и server, иначе задерживается до освобождения server (PDF 4 / печ. 226).

Таким образом, решение определяет не только назначение работ машинам, но и порядок использования общего server. Возникающий из-за server idle машин — эндогенный эффект расписания, а не заранее заданный множитель длительности.

### Методы доказательства

- Для unit processing times общая server sequence сводит задачу к соответствующей single-machine problem с processing times `p'_j=s_j`; completion time исходной работы равен completion time ее setup плюс единица (Theorems 3.1–3.2, PDF 6–7 / печ. 228–229).
- Polynomial algorithms получаются переносом правил EDD, SPT, Smith ratio и других классических sequencing results либо специальной alternating-machine construction (PDF 6–7, 9, 12–18 / печ. 228–229, 231, 234–240).
- Binary и unary NP-completeness доказываются редукциями из Partition, Numerical Matching with Target Sums, 3-Partition и известных machine-scheduling problems (PDF 7–17 / печ. 229–239).

## Релевантные результаты

### 1. Unit processing превращает common server в bottleneck

**Theorems 3.1–3.2 (PDF 6–7 / печ. 228–229).** Если `p_j=1`, то `s_j>=1`, и в active schedule server непрерывно занят на интервале от `0` до `sum_j s_j`. Server sequence взаимно однозначно соответствует single-machine sequence с `p'_j=s_j`. Для completion-time objectives выполняется сдвиг `C_j=C'_j+1`; для lateness и tardiness due dates сдвигаются как `d'_j=d_j-1`.

Это прямой scheduling result. Для M4 он показывает общий механизм: если последовательное обслуживание каждой задачи не короче параллельной processing phase, shared resource становится bottleneck независимо от числа машин. Но источник не переводит этот вывод в человеческую долю `h`, baseline speedup или AI workflow.

### 2. Makespan: hardness и специальные exact cases

**Theorem 4.1 (PDF 7 / печ. 229).** Recognition version `P2;S|s_j=1|C_max` binary NP-complete. Редукция из Partition использует две машины, единичные setup times и произвольные processing times.

Binary NP-completeness не исключает pseudo-polynomial algorithm. Table 1 прямо помечает pseudo-polynomial status как первоначально open и сноской сообщает, что его впоследствии разрешили Kravchenko and Werner; заключение указывает сложность `O(n sum_j p_j)` (PDF 5, 19 / печ. 227, 241).

**Theorem 4.2 (PDF 7–9 / печ. 229–231).** Recognition version `P2;S|s_j=s|C_max` unary NP-complete даже при одинаковой, но входной setup duration `s`. Доказательство использует Numerical Matching with Target Sums.

**Theorem 4.3 (PDF 9 / печ. 231).** `P;S|p_j=1|C_max` решается оптимально конструкцией с чередованием работ между двумя машинами. Нижняя граница задаётся полной server workload и единицей processing после последнего setup; построение достигает

```text
C_max = sum_j s_j + 1.
```

Авторы классифицируют этот случай как `O(1)` в своей таблице результатов. Содержательно это случай полного доминирования общего server: дополнительные машины сверх двух не уменьшают makespan.

### 3. Другие objectives

Карта результатов важна для точного описания вклада, хотя M0–M4 оптимизирует только makespan:

- `P2;S|s_j=1|L_max` unary NP-complete; при `p_j=1` EDD-based List решает `P;S||L_max` за `O(n log n)` (Theorems 5.1–5.2, PDF 9–12 / печ. 231–234).
- SPT оптимален за `O(n log n)` для `P2;S|s_j=1|sum C_j`; вариант с одинаковым произвольным `s` unary NP-complete (Theorems 6.1–6.2, PDF 12–15 / печ. 234–237).
- При `p_j=1` варианты `sum C_j` решаются через single-machine equivalence: constant-time construction для одинаковых setup times и `O(n log n)` при arbitrary `s_j` (Theorems 6.3–6.4, PDF 16 / печ. 238).
- `P2;S|s_j=1|sum w_j C_j` binary NP-complete; при `p_j=1` порядок по `s_j/w_j` оптимален за `O(n log n)` (Theorems 6.5–6.6, PDF 16–17 / печ. 238–239).
- Для late-jobs и tardiness criteria источник даёт сочетание unary/binary NP-completeness, polynomial algorithms и pseudo-polynomial algorithms, сведённое в Tables 2–3 (PDF 17–18 / печ. 239–240).

Эти результаты нельзя превращать в утверждение, что common-server scheduling «в целом NP-hard» или «в целом легко»: вычислительная сложность зависит от objective и от ограничений на `p_j`, `s_j` и `m`.

## Насколько common server близок к разработчику

### Входное окно

Setup у Hall является сильным структурным аналогом входного человеческого окна:

- server мощности 1 обслуживает не более одной задачи одновременно;
- setup task-specific через `s_j`;
- setup расположен до автономного processing;
- setup требует выбранную машину, то есть во время постановки соответствующий исполнитель уже зарезервирован;
- после setup машина работает unattended, а server может перейти к другой машине.

Так можно интерпретировать выдачу спецификации одному агенту перед автономным запуском. Более того, PDF прямо допускает human operator как server. Но это не делает `s_j` измерением времени разработчика: источник не изучает содержание, ошибки или когнитивную стоимость такой операции.

### Выходное окно

Аналогия не покрывает проверку результата. В модели Hall после processing работа завершена; server не возвращается для review, acceptance, исправления или интеграции. Поэтому выходное окно разработчика в M4 отсутствует.

Чтобы представить схему

```text
human specification -> agent processing -> human verification,
```

модель Hall пришлось бы расширить второй server operation после processing. Для циклов исправления потребовалась бы последовательность повторных human и agent phases. Алгоритмы и hardness results статьи доказаны не для такого расширения и автоматически на него не переносятся.

### Главное отличие от агрегата M4

Hall точнее M4 в одном узком отношении: `s_j` имеет явное временное положение и входит непосредственно в feasibility расписания. Агрегаты `h_i` и `H` в M4 сообщают объём человеческой работы, но сами по себе не определяют, приходится он на постановку, промежуточное вмешательство или выходную проверку.

M4 шире по предметной семантике: `h_i` может включать постановку, чтение, верификацию и направление исправлений, а `gamma(P)` — рост стоимости переключения. Однако bound `T_ai>=gamma(P)H` остаётся агрегированной нижней границей; для точного расписания M4 всё равно нужны явно размещённые human intervals. Hall даёт готовый шаблон только для одного входного интервала на задачу.

## Сопоставление с Kravchenko and Werner (1997)

Обе работы используют почти одно и то же scheduling core: одинаковые параллельные машины, nonpreemptive jobs и единственный server, выполняющий setup до processing. Различаются охват и центр анализа.

| Измерение | Hall et al. (2000) | Kravchenko and Werner (1997) |
|---|---|---|
| Основная цель | Карта сложности для восьми классических objectives | Более узкий анализ `C_max`, list-scheduling bounds и forced idle time `IT` |
| Нотация server | `Pm;S` или `P;S` | `P,S1` в локальной версии |
| Положение server operation | Setup/loading перед processing | Setup/loading перед processing |
| Makespan при `P2`, `s_j=1` | Theorem 4.1: binary NP-complete; pseudo-polynomial status передан Kravchenko and Werner | Точный pseudo-polynomial algorithm `O(n sum p_j)` |
| Arbitrary number of machines, `s_j=1` | Не основной новый makespan result статьи | Unary NP-hardness и анализ tight list-scheduling ratios |
| Отдельный induced-idle objective | Нет; machine idle обсуждается как следствие server interference | Есть objective `IT` и отдельные complexity/algorithm results |
| Unit processing `p_j=1` | Широкая equivalence с single-machine objectives | Не центральная линия вклада |
| Семантика server | Прямо допускаются human operator, robot, AGV или equipment | Формальный single server; developer semantics отсутствует |

Hall et al. сами называют Kravchenko and Werner “subsequent work”: Table 1 и заключение учитывают их pseudo-polynomial algorithm для первоначально открытого случая (PDF 5, 19 / печ. 227, 241). Это не противоречит библиографическому году 1997: формулировка отражает историю рукописи Hall et al., полученной в августе 1997 года и опубликованной в 2000 году.

Для M4 Hall полезнее как широкая карта objectives и как первичный источник, прямо допускающий человека в роли server. Kravchenko полезнее для более глубоких makespan guarantees и различения server workload и вызванного им forced idle. Ни одна работа не содержит выходной проверки разработчиком, task-precedence DAG или AI-specific параметров.

## Mapping `Z,k,r,P,W,L,C(P),h,H,gamma(P),makespan`

| Параметр M0–M4 | Статус | Что есть у Hall et al. | Граница сопоставления |
|---|---|---|---|
| `Z_i` | **absent** | Есть job-specific `p_j` и `s_j` | Нет baseline complexity без ИИ и единицы `X`; `p_j` и `s_j` — уже абсолютные durations разных операций |
| `k_i^(r)` / `k` | **absent** | — | Нет коэффициента изменения длительности относительно no-AI baseline и нет разложения `k=a+h` |
| `r` | **absent** | Анализируются разные классы input data (`p_j=1`, `s_j=1`, `s_j=s`) | Это не task/mode-specific режим взаимодействия и не выбор processing mode внутри одного instance |
| `P` | **direct** | `m`, целое число одинаковых параллельных машин | Прямой scheduling-аналог числа агентных слотов; effective real-valued parallelism M0 не поддерживается |
| `W` | **analogy** | Набор machine processing times `p_j` и server setup times `s_j`; в специальных proofs используются их суммы | Единого агрегата `W=X sum Z_i k_i` нет; machine и server workload имеют разные capacity constraints и не должны безусловно сливаться в `W/P` |
| `L` | **absent** | Есть внутренняя precedence каждой работы `setup -> processing` | Между различными jobs нет task-precedence DAG и critical-path length M2 |
| `C(P)` | **absent** | Server contention эндогенно создаёт machine idle time | Нет agent-agent integration work или множителя workload, зависящего от `m`; server-induced idle — не `C(P)` |
| `h_i` / `h` | **analogy** | Task-specific setup time `s_j` общего server; server может быть human operator | `s_j` не нормирован на baseline, охватывает только входной setup и не включает output verification |
| `H` | **analogy** | Полная server workload `sum_j s_j` | Это сумма setup operations, а не определённое авторами человеческое время постановки, чтения, проверки и исправления |
| `gamma(P)` | **absent** | — | Нет cognitive/context-switching penalty и нет зависимости `s_j` от числа машин; sequence-dependent switching times также не моделируются |
| makespan | **direct** | `C_max=max_j C_j` | Тот же тип fixed-set completion objective; нет no-AI baseline `T_h`, speedup `T_h/T_ai` или критерия ускорения |

Дополнительные величины источника — due dates `d_j`, weights `w_j`, lateness, tardiness и late-job indicators — не имеют прямых параметров в текущей M0–M4, потому что M0–M4 намеренно оптимизирует только makespan фиксированного workload.

## Что источник поддерживает

1. **Общий последовательный ресурс в parallel-machine scheduling не является новым primitive M4.** Hall et al. формализуют несколько параллельных исполнителей и один capacity-1 server, причём server может быть человеком (PDF 1–3 / печ. 223–225).
2. **Положение человеческой операции существенно.** Setup до processing должен быть явно размещён при одновременной доступности server и машины; сумма server work сама по себе не определяет допустимое расписание (PDF 1, 4 / печ. 223, 226).
3. **Shared-resource contention отличается от добавочной работы.** Server interference вызывает простой машин через ресурсную несовместимость, а не через множитель processing times. Это предупреждает против отождествления ожидания агентов с `C(P)`, `H` или `gamma(P)`.
4. **Makespan является только одним из возможных objectives.** Completion time проекта, занятость общего ресурса, ожидание машин и due-date criteria нельзя смешивать в одну метрику (PDF 4–5 / печ. 226–227).
5. **Даже один простой input setup радикально влияет на complexity.** Для makespan соседствуют binary NP-completeness, unary NP-completeness и exact unit-processing construction; сложность зависит от точных assumptions (PDF 5, 7–9 / печ. 227, 229–231).
6. **При доминировании server рост числа машин перестаёт помогать.** В `P;S|p_j=1|C_max` оптимум равен `sum s_j+1`, и две чередующиеся машины уже достигают bound (PDF 9 / печ. 231). Это прямой scheduling result, но только структурный аналог насыщения по человеческому ресурсу.

## Что источник не позволяет утверждать

- Что common server эмпирически или психологически эквивалентен вниманию разработчика.
- Что `s_j=h_i Z_i X`, `sum s_j=H` или что эти величины можно использовать без отдельного хронометража и калибровки.
- Что источник моделирует выходное окно проверки, acceptance, интеграцию результата, rework или несколько циклов общения с агентом.
- Что в источнике есть `Z`, task/mode-specific `k`, режим `r`, разложение `k=a+h`, `C(P)` или `gamma(P)`.
- Что server interference является switching penalty. Это ожидание машин из-за недоступности capacity-1 resource при фиксированных `s_j`.
- Что source model содержит software-task DAG или критический путь `L`: между jobs нет precedence constraints.
- Что Hall et al. оценивают speedup относительно одного разработчика без ИИ или оптимальное число кодовых агентов.
- Что `C_max=sum s_j+1` верно для arbitrary processing times. Это точный результат только для `p_j=1`.
- Что binary NP-completeness Theorem 4.1 исключает pseudo-polynomial algorithm: сама статья сообщает последующее решение Kravchenko and Werner.
- Что все common-server variants NP-hard: таблица содержит polynomial и constant-time special cases.
- Что algorithms и complexity results автоматически сохраняются после добавления post-processing verification, DAG, release dates, heterogeneous agents или context switching.
- Что aggregate bound `max{C(P)W/P,L,gamma(P)H}` следует из Hall et al. Источник строит другой, операционный resource-feasibility model.

## Отличие от M0–M4

| Измерение | Hall et al. (2000) | M0–M4 |
|---|---|---|
| Исследовательский вопрос | Оптимальные schedules и complexity при заданных `p_j`, `s_j` | Когда AI-конфигурация быстрее последовательного no-AI baseline |
| Workload | Заданные абсолютные setup и processing times | Baseline `Z_i X`, преобразованный task/mode-specific factor `k_i^(r)` |
| Исполнители | `m` identical parallel machines | `P` кодовых ИИ-агентов или рабочих потоков |
| Общий ресурс | Один server; одна setup operation до каждой работы | Один разработчик; постановка, чтение, верификация и направление исправлений |
| Положение human/server work | Явно до processing | В агрегате `h_i` не фиксировано; для точного schedule нужны отдельные интервалы |
| Выходная проверка | Отсутствует | Содержательно входит в `h_i` и практические M4 schedules |
| Зависимости | Только внутренняя цепочка setup–processing | Task DAG и critical path `L` на M2 |
| Overhead | Setup и server-induced idle моделируются операционно | Agent-agent overhead `C(P)` и human switching `gamma(P)` разделены |
| Неделимость | Setup и processing nonpreemptive | M0 идеально делим; M1 вводит неделимые задачи |
| Objective | Восемь classical criteria, включая `C_max` | Makespan и speedup относительно `T_h` |
| Результаты | Exact algorithms, equivalences и NP-completeness map | Lower bounds и criteria ускорения по уровням M0–M4 |

Hall et al. не являются «частным доказательством M4». Их постановка одновременно уже и точнее. Она уже, потому что моделирует только одно входное обслуживание и не содержит AI-specific layer, DAG и switching. Она точнее, потому что явно размещает setup и проверяет capacity двух ресурсов во времени. Корректное отношение таково: common-server scheduling — структурный предшественник точного фазового расширения M4, тогда как текущий M4 использует более широкий, но агрегированный human-work bound.

Отдельно источник проясняет неоднозначность ветви `W/P`. В Hall setup занимает и server, и целевую машину; следовательно, человеческая входная фаза резервирует один parallel slot. В человеко-агентном процессе это не всегда так: во время проверки результата агентный compute slot может быть свободен или уже выполнять другую работу. Поэтому перенос полного `W` в machine/agent workload требует явного решения, какие human phases занимают агентный слот.

## Проверенные тезисы синтеза

1. **Прямой результат:** Hall et al. задают deterministic nonpreemptive scheduling на identical parallel machines с одним common server; server выполняет task-specific setup/loading до processing и может обслуживать другую машину во время unattended processing (PDF 1–3 / печ. 223–225).
2. **Структурная аналогия:** setup operation хорошо моделирует входное окно одного разработчика перед автономной работой агента, но human semantics, нормировка через `h_i` и перенос на coding workflow принадлежат нашему сопоставлению, а не источнику.
3. **Отсутствующий механизм:** output verification, rework cycles, task DAG, AI mode `r`, effect factor `k`, agent overhead `C(P)` и switching penalty `gamma(P)` в модели Hall отсутствуют; поэтому algorithms и formulas статьи нельзя напрямую переносить на M4.
4. **Позиционирование вклада:** новизну M0–M4 нельзя строить на самом primitive «параллельные исполнители плюс один общий последовательный ресурс». Допустимый gap — совместная AI-specific параметризация baseline/duration, режимов, DAG, agent-agent overhead и нескольких человеческих фаз для fixed-workload software process.

## Короткий вариант встраивания в Related Work

> Hall, Potts, and Sriskandarajah (2000) рассматривают детерминированное nonpreemptive scheduling заданного множества работ на одинаковых параллельных машинах с одним common server. Перед processing каждой работы server выполняет task-specific setup/loading на выбранной машине; затем машина работает unattended, а server может обслуживать другую машину. Эта постановка является близким структурным предшественником M4 и прямо допускает human operator в роли server, но моделирует только входную операцию, а не выходную верификацию или циклы исправления. Авторы строят карту exact algorithms и NP-completeness для нескольких objectives: в частности, `P2;S|s_j=1|C_max` binary NP-complete, `P2;S|s_j=s|C_max` unary NP-complete, тогда как при `p_j=1` server становится bottleneck и оптимальный makespan равен `sum_j s_j+1`. В отличие от этой модели, M0–M4 связывает длительности с no-AI baseline через task/mode-specific `k_i^(r)`, допускает DAG и critical path `L`, разделяет agent overhead `C(P)` и human switching `gamma(P)`, а человеческое время включает постановку и проверку. Поэтому Hall et al. поддерживают shared-resource framing, но не формулы ускорения или AI-specific механизмы M0–M4.

## Итоговая оценка релевантности

Источник высокорелевантен как первичный формальный предшественник общего последовательного ресурса в системе параллельных исполнителей. По сравнению с общим амдаловским bound он даёт более конкретный механизм: server operation имеет task-specific duration, точное место до processing и capacity conflict, который может оставлять машины без работы. Для статьи M0–M4 это сильная опора против завышенной заявки о новизне общего ресурса и за необходимость явно планировать человеческие окна.

Одновременно Hall et al. не моделируют ячейку «разработчик — кодовые агенты» напрямую. Их common server покрывает максимум входную постановку; выходная проверка, исправление, DAG, task/mode-specific AI effect и зависящие от `P` издержки отсутствуют. Поэтому корректное использование источника — **direct** для parallel machines, common server, setup-before-processing и `C_max`; **analogy** для входного человеческого окна, `h` и `H`; **absent** для `Z`, `k`, `r`, `L`, `C(P)`, `gamma(P)` и выходной верификации.
