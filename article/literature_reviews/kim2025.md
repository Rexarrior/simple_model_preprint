# Kim et al. (2025/2026 v3): scaling agent systems, task-architecture alignment и границы переноса на звезду «один разработчик - `P` coding agents»

## Назначение и границы обзора

Этот документ разбирает Kim et al. применительно к модели M0-M4 для fixed-workload makespan ячейки «один разработчик - `P` кодовых ИИ-агентов». Работа нужна как современная эмпирика того, что польза multi-agent system зависит не от одного числа агентов, а от архитектуры координации, возможностей базовой модели и структуры задачи. Особенно релевантны результаты о decomposability, sequential interdependence, tool-related overhead, diminishing returns и topology-specific failure mechanisms.

Главная граница переноса принципиальна: Kim et al. сравнивают **LLM-agent architectures**, где координатор и исполнители сами являются LLM-backed agents. Человека, который ставит задачи, последовательно проверяет результаты и переключается между `P` потоками, в экспериментальном контуре нет. Primary outcome - task success/accuracy, а не elapsed time, latency или fixed-workload makespan. Поэтому относительные изменения `+80.8%` и `-70.0%` нельзя интерпретировать как ускорение, замедление времени или численные значения `k`.

Локальный PDF содержит 44 страницы; PDF-нумерация совпадает с напечатанной. Основной текст занимает страницы 1-28, references - 29-34, appendices - 35-44. Номера ниже относятся к PDF-страницам локальной копии.

## Исследовательские вопросы

Авторы формулируют три RQ (PDF с. 9-10):

1. **RQ1:** какие факторы определяют performance agent system - capability модели, coordination architecture, свойства задачи и их interactions?
2. **RQ2:** при каких условиях inter-agent coordination улучшает или ухудшает performance, в частности как результат модерируют decomposability, tool complexity и sequential dependencies?
3. **RQ3:** можно ли по измеримым свойствам модели, задачи и координации построить количественный принцип, предсказывающий лучшую agent architecture?

Тип доказательства - controlled benchmark evaluation плюс observational regression по полученным configuration-level measurements. Архитектуры, prompts, tools и computational budgets стандартизируются, однако task properties не рандомизируются: decomposability, sequentiality и tool count сравниваются главным образом между шестью разными benchmarks. Поэтому архитектурные contrasts внутри benchmark ближе к контролируемым, а moderator claims по свойствам задач имеют более слабую, междоменную идентификацию.

## Что именно считается agent system

Agent system задаётся как `S=(A,E,C,Omega)`: набор LLM-backed agents, environment, communication topology и orchestration policy. Каждый agent итеративно воспринимает environment, рассуждает, выбирает tool call и обновляет историю (PDF с. 6-8).

Человек в execution loop не участвует:

1. `orchestrator` в Centralized и Hybrid - LLM-backed agent, а не разработчик;
2. `aggregator` в Independent - программный/agent aggregation layer, а не human reviewer;
3. SWE-bench Verified и остальные environments исполняются автономными agent configurations;
4. paper не измеряет human active time, review queues, context switching человека или вмешательства оператора.

Следовательно, Centralized architecture визуально похожа на звезду, но её центральный узел - вычислительный agent, который можно масштабировать и запускать в рамках token budget. В M4 центральный узел - один capacity-1 developer с неразделимым вниманием. Эти системы структурно различны.

## Архитектурная taxonomy

Пять сравниваемых architectures образуют ablation по наличию orchestrator и peer communication (PDF с. 3, 7-8, 10, 12):

| Архитектура | Топология и policy | Основной механизм | Ограничение переноса |
|---|---|---|---|
| Single-Agent System (SAS) | Один reasoning locus, последовательный action-observation loop | Максимальная context integration, нет inter-agent messages | Не равен developer без AI; это один autonomous LLM agent |
| Independent MAS | Три изолированных workers передают outputs aggregator; synthesis-only, без peer exchange и analytical cross-validation | Parallel exploration / ensemble без error correction | Aggregation всё равно добавляет overhead; это не независимые coding tasks в общем repository |
| Centralized MAS | Три sub-agents плюс LLM orchestrator, hierarchical rounds | Decomposition, monitoring и verification bottleneck | Orchestrator не является shared human resource |
| Decentralized MAS | Три agents, all-to-all peer exchange, debate/consensus rounds | Information fusion и peer verification | Communication sequentializes debate и фрагментирует context |
| Hybrid MAS | Orchestrator плюс limited peer communication | Hierarchy и lateral exchange одновременно | Наиболее сложный protocol и наибольший measured overhead |

Для main implementation Appendix E указывает: SAS использует до 10 iterations; Independent - 3 agents; Centralized - 3 sub-agents, до 5 orchestration rounds и 3 iterations на agent в round; Decentralized - 3 agents, 3 debate rounds и 3 iterations на round; Hybrid объединяет centralized orchestration и peer phases (PDF с. 41). Публичный code repository содержит изменяемые configuration ceilings, поэтому для воспроизведения paper results нужен зафиксированный manuscript release/config, а не текущие defaults ветки `main`.

В taxonomy есть важная implementation-specific деталь. Основной текст определяет Independent aggregation как `synthesis_only`, без majority voting и аналитического сопоставления ответов (PDF с. 7). Поэтому его плохой результат нельзя обобщать на все independent ensembles или voting systems.

Основной grid включает три model families и capability range Intelligence Index 42-71 (PDF с. 12, 35-36):

| Family | Models в основном grid |
|---|---|
| OpenAI | GPT-5-nano, GPT-5-mini, GPT-5 |

ACI лучше связан с target, но требует предварительного запуска benchmark suite и потому не является полностью внешним capability covariate (PDF с. 17, 25, 35-36, 42).

## Scaling variable, controls и outcomes

### Что масштабируется

Работа использует сразу несколько axes, которые нельзя смешивать:

1. **Model capability:** Intelligence Index или ACI.
2. **Coordination architecture:** SAS, Independent, Centralized, Decentralized, Hybrid.
3. **Agent count `n_a`:** в основном grid почти фиксирован архитектурой (`1` для SAS, `3` workers и в hierarchical systems отдельный orchestrator); отдельный preliminary ablation варьирует `n_a in {1,3,5,7,9}`.
4. **Coordination intensity:** turns, message density, redundancy и trace-level error amplification.
5. **Task properties:** tool count, SAS baseline и benchmark-level domain characterization.

Поэтому статья является прежде всего исследованием **architecture x capability x task-domain**, а не чистым experiment `performance(P)` при неизменных topology, workload, latency budget и human supervision.

### Контроли

Авторы сохраняют одинаковыми task prompts, tool interfaces, observation structures и policies context truncation между architectures. Maximum total iterations и total reasoning-token budget стараются уравнять: main text сообщает mean около 4,800 reasoning tokens per trial, при этом MAS делит бюджет между parallel workers, а SAS получает больше последовательных rounds (PDF с. 3-4, 9, 12, 20-21, 41).

Такой matched-compute design хорошо изолирует эффект распределения фиксированного inference budget, но отвечает не на вопрос минимального wall-clock makespan при разрешённом росте compute. Parallel branches могут уменьшать latency ценой большего compute; paper называет этот trade-off будущим направлением и не измеряет его как primary outcome (PDF с. 26-27).

### Outcomes

Primary outcome - domain-specific task success/accuracy: factual correctness, task completion, goal satisfaction, patch resolution и т.п. Secondary outcomes - coordination turns/overhead, messages, redundancy, success per 1,000 tokens, dollar cost, factual/trace errors и information-gain proxies (PDF с. 11-13, 16, 20-24).

В статье нет:

- elapsed end-to-end latency одного configuration;
- fixed-workload completion time;
- project makespan;
- developer active time;
- quality-adjusted accepted-work time при едином human review gate.

## Основные результаты по benchmarks

Percentage annotations определены как `(mean_MAS - mean_SAS) / mean_SAS * 100%`. Это относительное изменение success/accuracy, усреднённое по models внутри benchmark и architecture, а не изменение времени (PDF с. 11, 13-14).

| Benchmark | SAS mean | Лучший MAS | Лучший relative delta | Худший / характерный negative delta | Evidence |
|---|---:|---|---:|---:|---|
| Finance Agent | `0.349` | Centralized `0.631` | `+80.8%` | Independent всё равно `+57%` | PDF с. 11, 13-14 |
| BrowseComp-Plus | `0.318` | Decentralized `0.347` | `+9.2%` | Independent `-35%` | PDF с. 11, 13 |
| PlanCraft | `0.568` | Hybrid `0.346` как least-worst MAS | `-39.1%` | Independent `0.170`, `-70.0%` | PDF с. 11, 13-15 |
| Workbench | `0.629` | Decentralized `0.664` | `+5.6%` | Independent около `-11%`; Centralized/Hybrid `-1.2%` | PDF с. 11, 13 |
| SWE-bench Verified | `0.522` | Hybrid `0.511` как least-worst MAS | `-2.1%` | Independent `0.444`, `-14.9%` | PDF с. 11, 14 |
| Terminal-Bench | `0.344` | Independent `0.350` | `+1.7%` | Centralized `0.278`, `-19.2%` | PDF с. 11, 14 |

### Точный смысл `+80.8%` и `-70.0%`

Для Finance Agent:

```text
(0.631 - 0.349) / 0.349 = 0.808...
```

Для PlanCraft Independent:

```text
(0.170 - 0.568) / 0.568 = -0.7007...
```

То есть проверенные headline values действительно равны примерно `+80.8%` и `-70.0%`, но это ratios средних success rates. Они не являются `80.8% faster`, `70% slower`, speedup `1.808x`, duration factor `k=0.192/1.70` или изменением makespan.

Статья не печатает отдельные confidence intervals именно для этих двух architecture-aggregated deltas. Общая агрегация по шести benchmarks даёт mean MAS improvement `-0.3%`, 95% CI `[-58.7%, +77.2%]`, `sigma=37.5%`, что подчёркивает extreme heterogeneity, а не средний универсальный effect (PDF с. 14). Для 20-instance SWE-bench/Terminal cells Appendix Table 16 даёт bootstrap intervals типичной ширины около `+/-20` percentage points (PDF с. 26, 43).

## Task-architecture alignment

### Decomposability

Finance Agent допускает параллельное исследование regulatory/news, SEC filings и operational impact с последующим synthesis. Centralized architecture совпадает с этой структурой и даёт `+80.8%`. Авторы подтверждают механизм qualitative trace comparison: SAS последовательно исследует источники, а MAS распределяет независимые информационные ветви (PDF с. 13-15).

Это сильное comparative evidence, что natural subtask boundaries делают coordination полезнее. Но decomposability не назначается случайно и не измеряется одной независимой task-level шкалой; вывод получен главным образом из contrast Finance Agent против PlanCraft и анализа traces.

### Sequentiality

PlanCraft требует state-dependent ordered actions. Artificial decomposition создаёт redundant research/inventory subtasks, сообщения и fragmented state tracking; все MAS variants ухудшают result от `-39.1%` до `-70.0%` (PDF с. 11, 13-15).

Для M2 это важная эмпирическая аналогия: высокая sequential interdependence ограничивает полезный parallelism. Однако paper не строит precedence DAG, не измеряет длину критического пути в единицах времени и не показывает, что negative accuracy delta является функцией нашего `L`. Его `L>3` в benchmark criteria означает длину action-observation trajectory, а не critical-path length M2 (PDF с. 9).

### Domain complexity score

Appendix C присваивает каждому benchmark score `D in [0,1]` из sequential interdependence, state-space complexity и **observed coordination-overhead sensitivity**, затем калибрует score против observed MAS patterns (PDF с. 38-39). Поскольку одна компонента `D` уже использует результат MAS-vs-SAS, threshold `D approximately 0.40` нельзя считать полностью независимым prospective predictor. Сами авторы признают, что одинаковые `D` у Finance (`0.407`) и PlanCraft (`0.419`) дают противоположные outcomes и что decomposability важнее scalar complexity.

## Tool use как moderator

Авторы оценивают interaction coordination efficiency x tool count как `beta=-0.096`, naive `p=0.002`, 95% CI `[-0.154,-0.037]`; Holm-adjusted `p=0.026`. Направление согласуется с тезисом, что tool-rich environments усиливают coordination tax (PDF с. 3-4, 17-18, 20, 25, 43).

Однако inference чувствителен к шести benchmark clusters:

- cluster-robust `p=0.205` для `efficiency_x_tools`;
- cluster-robust `p=0.172` для main effect `log_tools`;
- authors поэтому называют dataset-level effects directional patterns, а не окончательно подтверждёнными эффектами.

Кроме того, tool count принимает лишь шесть benchmark-level значений `{2,3,4,5,7,16}` и смешан с domain. Корректный claim: **данные совместимы с tool-coordination trade-off, но его magnitude и универсальность неопределённы**. Некорректный claim: «каждый дополнительный tool причинно уменьшает performance на 9.6%»; predictors стандартизированы, а coefficient нельзя умножать на raw tool count (PDF с. 17-18, 25).

## Capability saturation и diminishing returns

Paper сообщает threshold около `45%` SAS performance: при сильном single-agent baseline дополнительным agents остаётся меньше room for improvement, а coordination cost может доминировать. На SWE-bench Verified, где большинство SAS baselines выше threshold, все MAS architecture means немного хуже SAS (PDF с. 3-4, 14, 19, 25-27).

Статистическая картина требует точной оговорки:

1. main effect `single_agent_baseline` имеет naive `p=0.001`, cluster-robust `p=0.004`, Holm `p=0.018`;
2. interaction `baseline x log(1+n_a)`, непосредственно выражающий diminishing return от agent count, имеет `beta=-0.236`, naive `p=0.004`, но cluster-robust `p=0.105` и Holm `p=0.084`;
3. threshold `~0.45` получен из regression decision boundary после denormalization, а не preregistered cutoff;
4. reported `94%` match подтверждает threshold на 16 model x benchmark configurations только для SWE-bench Verified и Terminal-Bench.

Поэтому capability saturation - наиболее устойчивый общий pattern работы, но точное значение `45%` и interaction с числом agents следует считать оценочным engineering rule, не универсальным законом.

## Overhead и failure mechanisms

### Architecture-level measurements

Table 5 агрегирует execution traces по `N=260` и применяет architecture-level coordination metrics uniformly across benchmarks (PDF с. 20):

| Metric | SAS | Independent | Decentralized | Centralized | Hybrid |
|---|---:|---:|---:|---:|---:|
| Success rate | `0.466` | `0.370` | `0.477` | `0.463` | `0.452` |
| Turns | `7.2+/-2.1` | `11.4+/-3.2` | `26.1+/-7.5` | `27.7+/-8.1` | `44.3+/-12.4` |
| Overhead relative to SAS | `0%` | `58%` | `263%` | `285%` | `515%` |
| Message density | `0.00` | `0.00` | `0.41` | `0.39` | `0.24` |
| Redundancy | `0.00` | `0.48` | `0.50` | `0.41` | `0.46` |
| Coordination efficiency | `0.466` | `0.234` | `0.132` | `0.120` | `0.074` |
| Trace error amplification | `1.0` | `17.2` | `7.8` | `4.4` | `5.1` |
| Success per 1K tokens | `67.7` | `42.4` | `23.9` | `21.5` | `13.6` |

Эти measurements поддерживают topology-specific overhead, но не являются нашей функцией `C(P)`:

1. overhead определён через turns/messages и normalized compute, не через elapsed makespan multiplier;
2. metrics постоянны на уровне architecture и потому тесно связаны с architecture label;
3. main grid не варьирует `P` независимо от topology;
4. coordination can improve accuracy despite larger turns, поэтому cost и outcome образуют trade-off, а не один multiplicative slowdown.

### Error propagation и verification

Independent показывает trace-level amplification `17.2x`, 95% CI `[14.3,20.1]`, Centralized - `4.4x`, `[3.8,5.0]`. Авторы связывают разницу с validation bottleneck: orchestrator может перехватить contradiction, numerical drift и context omission до aggregation; Hybrid, напротив, добавляет coordination failures из-за protocol complexity (PDF с. 18, 20-23).

Но после включения других coordination metrics main regression effect error amplification незначим (`p=0.658`), как и interaction с tools (`p=0.332`). Значит, `17.2x` против `4.4x` описывает trace mechanism, но regression не устанавливает, что именно этот metric независимо причинно объясняет performance gap.

### Superlinear turns и предел team size

Авторы fit'ят architecture-aggregated relation

```text
Turns = 2.72 * (n + 0.5)^1.724,
R^2 = 0.974,
95% CI exponent [1.685,1.763].
```

и интерпретируют exponent `>1` как superlinear growth coordination work (PDF с. 21, 24). Отдельный Figure 5 варьирует `n_a in {1,3,5,7,9}` для Gemini 2.0 Flash и Gemini 2.5 Pro в Centralized/Decentralized systems и показывает interior optima/diminishing returns (PDF с. 23).

Эта часть является preliminary:

- caption Figure 5 не называет benchmark, что мешает точно привязать ablation к task distribution;
- tested models только две Gemini variants;
- topology и count effects полностью не ортогонализированы;
- power law fit строится по architecture-aggregated means, а не по независимому широкому ряду team sizes;
- main regression direct effect `log(1+n_a)` незначим (`p=0.487`).

Для статьи безопасен qualitative claim о finite optimum и diminishing returns; численный exponent нельзя переносить в `C(P)` или `gamma(P)`.

## Predictive model и его uncertainty

Полная regression использует 20 parameters: capability, tools, agent count, overhead, messages, redundancy, efficiency, error amplification, SAS baseline и девять interactions. При five-fold configuration-level cross-validation получено (PDF с. 16-20, 42):

| Capability metric | Train `R^2` | CV `R^2` | SD CV |
|---|---:|---:|---:|
| Intelligence Index | `0.463` | `0.373` | `0.170` |
| Agentic Capability Index | `0.481` | `0.413` | `0.130` |

`R^2` умеренный: модель объясняет часть, но далеко не всю variation. Experiment-level folds содержат configurations из тех же benchmarks; это не проверка на новом task domain. Leave-one-dataset-out показывает трудность absolute cross-domain prediction, а `87%` architecture-selection accuracy относится к within-domain held-out configurations (PDF с. 19, 25, 27).

Appendix B дополнительно сужает generalization claim. На трёх held-out frontier models в BrowseComp-Plus модель даёт MAS-only MAE `0.061`, но **предсказывает Hybrid лучшей architecture для всех трёх**, тогда как фактически лучшие результаты дают Centralized или Decentralized. Hybrid overprediction в среднем составляет `+37.0%` (PDF с. 36-38). Поэтому нельзя писать, что framework надёжно выбирает optimal architecture для unseen frontier models; корректнее говорить о частичной calibration relative MAS performance внутри одного известного benchmark.

## Внутренние несогласованности, которые нельзя переносить

1. На PDF с. 13 и Figure 2 Workbench Hybrid имеет mean около `0.621`, то есть примерно `-1.2%` против SAS `0.629`. На PDF с. 18 текст внезапно приводит `0.21 on Workbench` для Hybrid. Это противоречит основной таблице/figure и соседним значениям; число `0.21` использовать нельзя без проверки source data.
2. Table 5 сообщает matched total reasoning tokens, но overhead определяется через turns и далее местами описывается как `1.6-6.2x token budgets`. Для M0-M4 safest interpretation - measured coordination work/cost proxy, а не единый token или latency multiplier.
3. Domain complexity `D` частично использует observed coordination sensitivity, поэтому его нельзя одновременно подавать как полностью независимое объяснение тех же outcomes.
4. Abstract создаёт более сильное впечатление transfer architecture preferences на unseen frontier models, чем Appendix B, где optimal architecture prediction не срабатывает ни для одной из трёх models.

### Что остаётся невоспроизведённым в этом обзоре

Полный rerun не выполнялся: он требует платных API OpenAI/Google/Anthropic, Docker-based benchmarks и значительного inference budget. Поэтому обзор проверяет paper, arXiv metadata и наличие artifacts, но не подтверждает numerical results независимым повторным вычислением.

Ограничения reproducibility:

1. API model names не гарантируют immutable checkpoints; sampling/backend behavior мог измениться.
2. Claude Sonnet 3.7 уже deprecated, что прямо сократило grid в ходе самой работы.
3. Intelligence Index частично реконструирован авторами, некоторые components approximate.
4. Finance/Workbench требуют setup/download upstream data; external services и web results могут меняться.
5. BrowseComp-Plus использует dynamic web environment, а значит exact replay зависит от состояния внешнего мира и search tooling.
6. `main` repository может расходиться с paper run; воспроизводить следует version-specific tag и saved configs.
7. Representative traces sanitized, поэтому они не обязательно позволяют полностью audit'ить все 260 configurations.

## Ограничения

### Признанные авторами

1. Основное сравнение охватывает canonical, но не все возможные architectures; scaling до 9 agents предварительный (PDF с. 25).
2. Agents в основном используют одинаковые base architectures и role prompts; heterogeneous teams изучены лишь в 13 BrowseComp-Plus configurations (PDF с. 26, 42).
3. Tool-heavy coordination protocols специально не оптимизированы (PDF с. 26).
4. Prompts одинаковы для experimental control, но не tuned per model или architecture (PDF с. 26).
5. Шесть benchmarks не покрывают embodied, multimodal, multi-user и long-horizon real-world feedback loops (PDF с. 26-27).
6. SWE-bench/Terminal используют только по 20 instances; cell-level intervals широки (PDF с. 26, 43).
7. Token communication создаёт latency/cost floor; latent communication может изменить observed scaling (PDF с. 26-27).
8. Всего шесть dataset clusters; cluster-robust inference conservative, многие naive significant moderators теряют significance (PDF с. 25, 27, 43).
9. Absolute cross-domain prediction ограничено; transfer сильнее для relative patterns внутри известных regimes (PDF с. 25, 27, 36-38).

### Дополнительные ограничения для M0-M4

1. **Outcome mismatch:** success/accuracy не является duration ratio или makespan.
2. **Нет human supervisor:** central verification выполняет LLM orchestrator, поэтому `h`, `H` и `gamma(P)` отсутствуют.
3. **Workload mismatch:** benchmark instances повторяются для каждой configuration, но не планируются как один project с общей completion boundary.
4. **Нет wall-clock schedule:** parallelization factor и sequential depth описаны complexity notation, а не start/finish intervals resource-feasible schedule.
5. **`P` смешан с architecture:** main grid не даёт чистой dose-response curve по числу исполнителей.
6. **`L` mismatch:** sequential trajectory и task interdependence не равны duration-weighted critical path.
7. **`C(P)` mismatch:** turns/messages/tokens не являются multiplicative elapsed-time overhead agent integration.
8. **Coding evidence ограничено:** SWE-bench - только один из шести benchmarks и использует 20-instance subset; headline `+80.8/-70.0` получен не на coding tasks.
9. **Quality gate отличается:** benchmark validators оценивают task success, но нет human acceptance, maintainability, security и long-term rework.
10. **Compute regime специфичен:** fixed token budget исследует allocation compute, тогда как M0-M4 допускает parallel agent execution и оптимизирует elapsed makespan.
11. **Architecture metrics partly constructed:** несколько regression predictors являются architecture-level constants, что ограничивает независимую интерпретацию coefficients.
12. **Fresh preprint:** версия быстро менялась между декабрём 2025 и апрелем 2026; статус peer review не установлен.

## Полный mapping `Z,k,r,W,P,L,C(P),h,H,gamma(P)`

Здесь **direct** означает измеряемый объект с близким смыслом, **conceptual** - полезный механизм без численной совместимости, **mismatch** - одноимённая или близкая величина с другой физической семантикой, **absent** - объект отсутствует.

| Поле M0-M4 | Статус | Соответствие у Kim et al. | Точная граница переноса |
|---|---|---|---|
| `Z_i` / `Z` | **conceptual** | Benchmarks и instances различаются по difficulty, task structure, decomposability и sequentiality; SAS baseline служит difficulty proxy | Нет baseline human duration `Z_i X`, task weights или общей software complexity scale |
| `k_i^(r)` / `k` | **absent для time model** | Architecture-specific relative accuracy меняется от `+80.8%` до `-70.0%` | Accuracy ratio нельзя преобразовать в duration ratio `T_i^ai/(Z_i X)`; elapsed time не измерен |
| режим `r` | **conceptual, но semantic mismatch** | Coordination architecture задаёт system regime: independent/centralized/decentralized/hybrid | `r` M0-M4 описывает human-agent workflow конкретной task; здесь варьируется agent-agent topology без человека |
| `W = X sum Z_i k_i` | **absent** | Configurations получают общий benchmark corpus и matched compute budget | Corpus score и token budget не являются суммой duration-weighted fixed work |
| `P` | **direct как agent count, mismatch по topology** | `n_a` явно входит в regression; main systems используют 1 или несколько agents; ablation до 9 | Нет одного developer, число workers смешано с architecture, а `P` не является effective parallelism makespan schedule |
| неделимость / M1 | **conceptual** | Benchmark instances дискретны, subtask decomposition может быть полезной или искусственной | Нет assignment fixed jobs по identical executors, longest-job duration `M_N` или makespan bound |
| `L` / M2 | **conceptual, notation mismatch** | Sequential interdependence и action-observation trajectory `L>3`; PlanCraft показывает вред artificial decomposition | Нет DAG и critical-path length в единицах времени; paper's `L` - trajectory length, не наш `L` |
| `C(P)` / M3 | **conceptual support** | Turns, messages, overhead `0-515%`, superlinear turn growth и topology-specific coordination failures | Не elapsed integration multiplier; зависит от architecture и compute convention, а не только `P`; shared-code merge/coherency отдельно не измерены |
| `h_i^(r)` / `h` | **absent** | Centralized verification существует как LLM step | Нет human-active interval или developer review time; LLM verifier нельзя считать человеческой долей |
| `H = X sum Z_i h_i` | **absent** | Orchestrator bottleneck может sequentialize computation | Он не capacity-1 human resource и не сумма human service intervals fixed workload |
| `gamma(P)` | **absent** | Message/context fragmentation растёт в MAS | Это agent-side communication tax, не human context-switch penalty между `P` coding streams |
| Makespan | **absent** | Есть accuracy, turns, token efficiency и cost | Нет elapsed completion time набора задач, общего project finish или feasible human-agent schedule |

### Полный mapping к уровням M0-M4

| Уровень | Что требует M0-M4 | Что даёт Kim et al. | Вердикт |
|---|---|---|---|
| M0 | Fixed work `W`, time coefficient `k`, ideally divisible work и `W/P` | Matched benchmark instances и compute, но outcome success/accuracy | Поддерживает лишь идею, что parallel architecture benefit configuration-specific; не калибрует `W/P` или `k` |
| M1 | Неделимые jobs и lower bound по longest duration | Discrete benchmark tasks и qualitative decomposition examples | Нет durations, allocation или `M_N`; numerical validation отсутствует |
| M2 | Precedence DAG и critical path `L` | Сильный Finance-vs-PlanCraft contrast decomposable против sequential tasks | Лучшая эмпирическая опора task-architecture alignment, но не измерение DAG/makespan bound |
| M3 | Agent integration multiplier `C(P)` | Rich evidence turns/messages/redundancy/error/coordination overhead by topology | Концептуально поддерживает scale- и topology-dependent overhead; reported percentages нельзя подставлять в `C(P)` |
| M4 | Один developer, `k=a+h`, capacity-1 `H`, non-overlapping verification windows и `gamma(P)` | Human execution resource отсутствует | Не поддерживает M4 количественно и не является one-human-many-code-agents experiment |

## Что источник поддерживает для нашей статьи

1. **Architecture-task alignment:** coordination полезна, когда задача естественно decomposable, и вредна при strict sequential interdependence (PDF с. 11, 13-15).
2. **Нет универсального multi-agent gain:** aggregate mean близок к нулю при огромной heterogeneity; результат зависит от domain и topology (PDF с. 11, 14).
3. **`P` недостаточно:** прямой agent-count effect незначим, а architecture и task structure важнее простого добавления workers (PDF с. 20, 23-25).
4. **Finite useful scale:** turns растут superlinearly, а agent-count ablation показывает interior optima/diminishing returns, хотя точная функция пока preliminary (PDF с. 21, 23-25).
5. **Coordination имеет несколько механизмов:** decomposition, communication, redundancy, verification, error propagation и protocol failures нельзя свести к одному pairwise channel count (PDF с. 7-8, 18-24).
6. **Central verification может сдерживать ошибки:** trace-level error amplification ниже у Centralized, чем у Independent (PDF с. 18, 20-23).
7. **Tool-rich workflows могут усиливать coordination tax:** направление поддержано naive/Holm analysis, но cluster-robust uncertainty обязательна (PDF с. 17-18, 25, 43).
8. **Strong SAS leaves less headroom:** capability saturation - наиболее устойчивый pattern, но `45%` является estimated threshold (PDF с. 19-20, 25-27).
9. **Coding domain не гарантирует MAS benefit:** на 20-instance SWE-bench Verified subset все architecture means ниже SAS от `-2.1%` до `-14.9%` (PDF с. 11, 14, 26, 43).
10. **Empirical coordination metrics полезнее голой architecture label, но prediction partial:** CV `R^2` остаётся `0.373/0.413`, cross-domain transfer ограничен (PDF с. 16-20, 25, 27).

Пункты 3-5 и сопоставление с `C(P)` являются синтезом paper в терминах M0-M4, а не формулировками авторов.

## Что источник не позволяет утверждать

1. Что multi-agent systems ускоряют работу на `80.8%` или замедляют её на `70%`.
2. Что `+80.8/-70.0` можно преобразовать в `k`, speedup или makespan.
3. Что adding agents всегда помогает decomposable tasks или всегда вредит sequential tasks вне tested benchmarks.
4. Что `P=3`, `P=7` или иной count оптимален для coding agents под контролем разработчика.
5. Что exponent `1.724` является универсальной функцией `C(P)`.
6. Что tool count причинно определяет coordination loss; cluster-robust tests по шести datasets не подтверждают этот moderator на 5% уровне.
7. Что точный universal capability threshold равен `45%`.
8. Что Independent MAS вообще не умеет исправлять ошибки; tested implementation использует synthesis-only без analytical voting.
9. Что Centralized architecture моделирует человека как orchestrator или подтверждает capacity-1 human bottleneck.
10. Что можно оценить `h`, `H`, intervention windows или `gamma(P)`.
11. Что SWE-bench result описывает production developer productivity, maintainability или accepted project work; это autonomous benchmark success на 20 instances per configuration.
12. Что framework выбирает optimal architecture на новом domain: `87%` относится к within-domain held-out configurations.
13. Что optimal architecture selection уже перенеслась на unseen frontier models; Appendix B показывает ошибочный выбор Hybrid для всех трёх held-out models.
14. Что all reported numerical details internally consistent; Workbench Hybrid `0.21` на с. 18 конфликтует с main results.
15. Что источник peer-reviewed; проверенная версия - arXiv v3, а repository сообщает лишь ongoing review.

## Отличие от M0-M4

| Измерение | Kim et al. | M0-M4 |
|---|---|---|
| Центральный вопрос | Когда LLM-agent coordination architecture повышает task success при matched compute | Когда один developer с `P` coding agents сокращает fixed-workload makespan |
| Топология | Один или несколько communicating LLM agents; LLM orchestrator | Star topology с одним capacity-1 human и `P` agent executors |
| Workload | Повторяемые benchmark instances, каждая configuration оценивается отдельно | Один fixed set software jobs с общей completion boundary |
| Outcome | Accuracy/success, turns, token efficiency, cost, trace errors | Elapsed makespan и speedup относительно sequential human baseline |
| Scaling axis | Capability, architecture, coordination metrics; count частично | Explicit `P` в одном process regime с task durations и resources |
| Decomposability | Benchmark-level task characteristic, qualitative trace analysis | Explicit task decomposition, indivisible jobs и DAG |
| Sequentiality | Environment/action dependence | Duration-weighted critical path `L` |
| Coordination | Messages, rounds, redundancy, verification и agent error propagation | `C(P)` для integration плюс `gamma(P)H` для human switching |
| Human role | Отсутствует в execution loop | Постановка, verification и correction образуют `h_i` и общий `H` |
| Compute | Matched reasoning-token/iteration budget | Compute cost вне objective; parallel execution влияет на elapsed time |
| Validation | Benchmark pass/fail и domain validators | Fixed acceptance gate должен входить в task duration; external `k/h` calibration |

Kim et al. находятся рядом с M2-M3, но не с M4. Они дают сильную современную иллюстрацию того, что decomposability, sequentiality и coordination topology изменяют результат, и показывают измеримые agent-side overhead/failure mechanisms. M0-M4 добавляет другой объект оптимизации и отсутствующий ресурс: elapsed makespan fixed software workload, где `P` autonomous coding streams конкурируют за последовательное внимание одного разработчика.

## Проверенные claims для Related Work

1. В arXiv v3 Kim et al. сравнили 260 configurations на шести agentic benchmarks, пяти architectures и девяти моделях трёх families; для двух Docker-heavy benchmarks использованы восемь моделей и 20-instance subsets (PDF с. 1, 3, 9-12, 26-27).
2. Relative success/accuracy change относительно SAS ranged from `+80.8%` для Centralized Finance Agent (`0.631` против `0.349`) до `-70.0%` для Independent PlanCraft (`0.170` против `0.568`) (PDF с. 11, 13-15).
3. Контраст поддерживает task-architecture alignment: естественно decomposable financial research выигрывает от parallel specialization/synthesis, а sequential state-dependent planning страдает от artificial decomposition и fragmented context (PDF с. 13-15).
4. Coordination overhead зависит от topology: turns растут от `7.2` у SAS до `44.3` у Hybrid, а trace-level error amplification составляет `17.2x` для Independent и `4.4x` для Centralized; regression, однако, не подтверждает independent main effect error amplification (PDF с. 18, 20-23).
5. Tool-coordination interaction равна `beta=-0.096`, naive `p=0.002` и Holm `p=0.026`, но cluster-robust `p=0.205`; поэтому это directional evidence, не установленный universal effect (PDF с. 17-18, 25, 43).
6. Full regression достигает five-fold CV `R^2=0.373`, либо `0.413` с ACI; `87%` architecture selection относится к held-out configurations внутри известных task regimes, а не к новым domains (PDF с. 17-20, 25, 27, 42).
7. На трёх held-out frontier models в BrowseComp-Plus MAS-only MAE равно `0.061`, но model incorrectly predicts Hybrid optimal in all three; transfer architecture selection остаётся preliminary (PDF с. 36-38).
8. В execution loop нет человека, поэтому source не валидирует `h`, `H`, `gamma(P)` или topology «one human-many coding agents».

## Встраивание в статью

### Рекомендуемое место

Источник лучше поставить в подраздел **Scalability laws and coordination overhead** после Amdahl/Gustafson/Gunther и Brooks, но до scheduling/common-server и human-supervision literature.

Его функция в narrative:

1. дать современное empirical evidence, что scaling зависит от task architecture, а не только `P`;
2. поддержать необходимость `L` и topology-dependent `C(P)` на conceptual level;
3. показать finite returns и failure mechanisms;
4. затем явно провести границу: Kim et al. не моделируют shared human attention, поэтому переход к common-server scheduling, fan-out и M4 остаётся самостоятельным вкладом нашей постановки.

### Безопасный короткий вариант для `Related Work`

> Kim et al. сравнили 260 configurations пяти single- и multi-agent architectures на шести agentic benchmarks и девяти LLMs. Относительное изменение task success против single-agent baseline варьировалось от `+80.8%` для centralized coordination на decomposable financial reasoning до `-70.0%` для independent agents на sequential planning. Execution traces связывают gains с естественной декомпозицией и verification, а losses - с context fragmentation, redundant work и coordination failures; tool-related overhead и capability saturation дополнительно указывают на diminishing returns. Эти результаты поддерживают зависимость эффективности от task-architecture alignment и необходимость topology-dependent coordination term. Однако reported percentages относятся к accuracy/success при matched inference budget, а не к времени: исследование не измеряет fixed-workload makespan и не включает человека в execution loop. Поэтому оно не калибрует `k`, `h`, `H` или `gamma(P)` для звезды «один разработчик - `P` coding agents».

### Формулировка для discussion/limitations

> Современная multi-agent benchmark evidence показывает, что architecture selection может менять success как в положительную, так и в отрицательную сторону, особенно при различиях в decomposability и sequential interdependence. Тем не менее эти оценки нельзя напрямую использовать как множители времени: benchmark success, token/turn overhead и elapsed project makespan являются разными outcomes. Кроме того, agent-agent architectures без human supervisor не выявляют очередь постановки и верификации, которая в M4 задаётся общим ресурсом `H` и switching penalty `gamma(P)`.

## Итоговая оценка источника

Kim et al. - наиболее прямой современный источник в корпусе для тезиса, что scaling agent systems определяется alignment между task structure и coordination architecture. Сильные стороны - controlled comparison пяти topologies, шесть genuinely interactive benchmarks, три model families, process metrics, explicit uncertainty corrections и открытый repository. Особенно полезен contrast между decomposable Finance Agent и sequential PlanCraft: он показывает, почему одинаковое добавление agents может дать противоположный знак результата.

Доказательная сила для M0-M4 заканчивается перед time-and-human scheduling layer. Headline deltas относятся к benchmark success, main grid смешивает agent count с topology, moderator inference опирается лишь на шесть domains, а frontier validation не подтверждает reliable optimal-architecture selection. Главное отличие - полное отсутствие shared developer. Поэтому корректная роль Kim et al. в статье - эмпирическая опора task-architecture alignment, diminishing returns и agent-side coordination mechanisms для M2-M3. Некорректная роль - численная калибровка `k`, `C(P)` как makespan multiplier или подтверждение M4 для one-human-many-code-agents.
