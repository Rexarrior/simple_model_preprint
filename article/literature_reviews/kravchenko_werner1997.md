## Вопрос и вклад статьи

Статья исследует детерминированное планирование `n` работ на `m` одинаковых параллельных машинах, когда перед обработкой каждой работы требуется операция setup, выполняемая единственным общим server. Основные вопросы таковы:

1. Когда специальные варианты задачи минимизации makespan допускают точный псевдополиномиальный алгоритм?
2. Какие варианты остаются NP-трудными даже при единичных или одинаковых setup times?
3. Какие worst-case bounds имеют простые list-scheduling heuristics и являются ли эти bounds точными?
4. Как меняются сложность и разрешимость, если вместо makespan минимизировать вынужденный простой машин из-за занятости server?

Собственный вклад авторов, отделённый от результатов предшествующих работ:

- псевдополиномиальное точное решение `P2,S1 | s_i = 1 | C_max` через преобразование расписания для `P2 || C_max` (Theorem 1; PDF/локальная печ. стр. 3–8);
- доказательство unary NP-hardness задачи `P,S1 | s_i = 1 | C_max`, когда число машин входит во вход (Theorem 2; стр. 8–9);
- доказательство tightness ранее полученных коэффициентов `2 - 1/m` для LPT и `3 - 2/m` для произвольного list schedule даже при `s_i = 1` (стр. 9–12);
- полиномиальный алгоритм для `P2,S1 | s_i = 1 | IT` (Theorem 3; стр. 12–13);
- усиление известной сложности критерия forced idle time: `P2,S1 | s_i = s | IT` unary NP-hard уже при одинаковых setup times (Theorem 4; стр. 13–15);
- два полиномиально разрешимых случая для `IT` при `p_i > s` и `p_i < s` (Propositions 1–2; стр. 15–16).

Введение статьи отдельно сообщает как **известные из работы [2]**, а не новые результаты Kravchenko and Werner: линейную разрешимость `P,S1 | s_i, p_i = 1 | C_max`, binary NP-hardness `P2,S1 | s_i = 1 | C_max` и unary NP-hardness `P2,S1 | s_i = s | C_max` (стр. 2). Аналогично коэффициенты list scheduling на стр. 10 сначала атрибутированы [2]; новая часть данной статьи состоит в доказательстве их tightness для единичных setup times.

## Постановка и метод

### Ресурсы и работы

Постановка на PDF/локальной печ. стр. 2 задаётся следующим образом:

- имеются `m` одинаковых параллельных машин и `n` заданных работ;
- все работы доступны в момент времени 0;
- работа `i` имеет известное целое processing time `p_i` и известное целое loading/setup time `s_i`;
- непосредственно перед обработкой работу необходимо загрузить на выбранную машину;
- setup выполняет единственный server, общий для всех машин;
- после завершения setup server освобождается и может обслуживать другую машину;
- времена перемещения server между машинами приняты равными нулю;
- одна машина обрабатывает не более одной работы одновременно;
- preemption запрещён;
- `p_i = 0` допускается и интерпретируется как пренебрежимо малая положительная обработка.

Таким образом, server требуется **ровно для setup/loading перед processing каждой работы**. Он не выполняет саму обработку, не участвует после неё в приёмке результата и не моделирует повторные циклы исправления. Одновременные запросы нескольких машин к server могут создать вынужденный простой машины.

### Objectives

Статья рассматривает два разных objective.

1. **Makespan `C_max`.** Требуется назначить и упорядочить все работы так, чтобы минимизировать максимальное время завершения. Обозначение авторов: `P,S1 | s_i | C_max`, где `S1` указывает на один server (стр. 2).
2. **Forced idle time/interference `IT`.** Считается время, когда машина в list schedule простаивает именно потому, что нужный для setup server недоступен. Не учитывается хвостовой простой машины после завершения всей назначенной ей обработки, пока другая машина ещё работает. Авторы подчёркивают, что учёт и такого хвоста привёл бы обратно к makespan criterion (стр. 2, 12–16).

`IT` не является ни суммарным временем работы server, ни человеческим временем `H`: это вызванное конкуренцией ожидание машин.

### Методы

- Для `P2,S1 | s_i = 1 | C_max` авторы включают единичный setup в modified processing time `p'_i = p_i + 1`, строят оптимальное расписание `P2 || C_max`, сдвигают загрузку одной машины на единицу и преобразуют расписание так, чтобы одновременно не начинались две работы. Первая единица `p'_i` трактуется как использование server (стр. 3–8).
- Для NP-hardness используются редукции из `3-partition` (Theorems 2 и 4; стр. 8–9 и 13–15).
- List schedule задаётся перестановкой работ, определяющей последовательность setup на server. Очередную работу назначают машине, которая освободится первой, а setup выполняют настолько рано, насколько это возможно (стр. 9–10).
- Для единичных setup times и `IT` работы разделяются на `A = {i: p_i = 0}` и `B = {i: p_i != 0}`; `B` сортируется по неубыванию `p_i`, после чего применяется специальное правило выбора следующей работы (стр. 12–13).

## Определения, теоремы и результаты

### Базовая scheduling model

**Определение `P,S1 | s_i | C_max` (PDF/локальная печ. стр. 2).** `P` означает одинаковые параллельные машины, `S1` — один server для setup, `s_i` — setup times, `C_max` — makespan. В рассматриваемой модели нет precedence DAG между работами: все работы готовы в нулевой момент.

**Определение `IT` (стр. 2).** Forced idle time — простой из-за того, что машина готова к следующей работе, но server занят setup на другой машине. Терминальный дисбаланс загрузки после завершения обработки на одной машине из `IT` исключён.

### Makespan

**Theorem 1 (стр. 6; доказательство стр. 6–8).** Предложенный авторами алгоритм строит оптимальное расписание для `P2,S1 | s_i = 1 | C_max`. Построение опирается на оптимальное решение `P2 || C_max` с `p'_i = p_i + 1`. Само преобразование такого расписания требует `O(n log n)`, а итоговая разрешимость остаётся псевдополиномиальной из-за исходного точного решения двухмашинной partition-like задачи (стр. 8).

Этот результат не означает полиномиальную разрешимость по длине двоичного входа: на стр. 2 binary NP-hardness того же варианта приведена как известный результат [2]. Псевдополиномиальный алгоритм этому утверждению не противоречит.

**Theorem 2 (стр. 8–9).** `P,S1 | s_i = 1 | C_max` unary NP-hard, если число одинаковых машин произвольно и входит во вход. Доказательство использует `3-partition`, задавая `3m` работ, `m` машин, `s_i = 1` и `p_i = m a_i - 1` (стр. 8–9).

**List-scheduling results (стр. 9–12).** Для `P,S1 | s_i | C_max` работа [2] дала worst-case ratios:

- LPT: `2 - 1/m`;
- произвольный list schedule: `3 - 2/m`.

Kravchenko and Werner строят семейства примеров и показывают, что обе границы tight даже при `s_i = 1`: соответствующие отношения стремятся к указанным константам при росте параметра `k` (стр. 10–12). Это guarantees относительно оптимального makespan в их single-server scheduling model, а не относительно baseline одного разработчика без ИИ.

### Forced idle time

**Theorem 3 (стр. 13; алгоритм стр. 12–13).** Специальный алгоритм определяет оптимальное расписание для `P2,S1 | s_i = 1 | IT`. С учётом сортировки положительных `p_i` вариант решается за `O(n log n)` (утверждение о сложности сформулировано при вводе алгоритма на стр. 12).

**Theorem 4 (стр. 13–15).** `P2,S1 | s_i = s | IT` unary NP-hard даже при одинаковой длительности setup всех работ. Это усиливает приписанный [3] результат для произвольных setup times.

**Proposition 1 (стр. 16).** Если `s_i = s` и `p_i > s` для всех работ, то `P2,S1 | s_i = s, p_i > s | IT` решается правилом SPT за `O(n log n)`; доказательство устанавливает `IT = s`.

**Proposition 2 (стр. 16).** Если `s_i = s` и `p_i < s` для всех работ, задача `P2,S1 | s_i = s, p_i < s | IT` решается за `O(n)`. Для list order `pi` авторы получают

`IT = (n - 1)s - sum_{i=1}^{n-2} p_{pi_i}`,

поэтому достаточно определить две работы с наименьшими processing times, не входящие в максимизируемую сумму первых `n - 2` позиций.

## Сходство с конфигурацией «один разработчик — несколько агентов»

Сходство является **структурным**, а не семантическим.

- `m` параллельных машин дают прямой scheduling-аналог нескольких одновременно выполняющих задачи агентов.
- Единственный server задаёт ресурс мощности 1, операции которого нельзя накладывать друг на друга. В этом ограниченном смысле он аналогичен одному разработчику, который не может одновременно поставить или проверить несколько задач.
- Конкуренция машин за server показывает, почему расписание, допустимое только по параллельным исполнителям, может потребовать явного планирования окон общего ресурса.
- Makespan `C_max` непосредственно совпадает по типу objective с временем завершения фиксированного набора задач в M0–M4.
- Результаты сложности показывают, что добавление даже очень простой общей setup-операции делает задачу планирования нетривиальной; баланс одной лишь суммарной машинной загрузки недостаточен.

Однако механический server **не следует отождествлять с человеческим вниманием**. В статье server выполняет заранее известную loading/setup operation до processing, имеет нулевое travel time и не интерпретирует постановку, не оценивает качество результата, не инициирует исправления и не восстанавливает контекст. Человеческое участие в M4 может возникать до, во время и после agent processing, а его длительность и содержание зависят от задачи и режима взаимодействия.

## Mapping к параметрам M0–M4

Статус `direct` означает, что источник непосредственно содержит соответствующую scheduling-конструкцию; `analogy` — что сопоставление вводится для синтеза и не является утверждением авторов; `absent` — что конструкции в собственной модели источника нет.

| Параметр M0–M4 | Статус | Что есть в источнике | Ограничение сопоставления |
|---|---|---|---|
| `Z_i` | analogy | Индексированные работы с известными `p_i` и `s_i` | Нет baseline complexity `Z_i` и единицы `X`; `p_i` — уже машинное processing time, а `s_i` — отдельная setup operation |
| `k_i^(r)` / `k` | absent | — | Нет ИИ, коэффициента изменения трудоёмкости или сравнения с работой без ИИ |
| `r` | absent | — | Нет интерактивного, делегированного или иного task/mode-specific режима |
| `P` | direct | `m` одинаковых параллельных машин | `m` — целое физическое число машин, тогда как `P` статьи M0–M4 может также обозначать эффективный средний параллелизм агентов |
| `W` | analogy | Суммарные processing и setup durations; при `s_i=1` используется `p'_i=p_i+1` | Источник не сводит всё к одной идеально делимой работе `W/P`; server workload имеет отдельное capacity constraint |
| `L` | absent | — | Все работы доступны в момент 0; task-precedence DAG и критический путь не заданы |
| `C(P)` | absent | — | Нет agent-agent integration overhead или множителя, зависящего от числа машин; induced idle `IT` — другая величина |
| `h_i` / `h` | analogy | Task-specific setup time `s_i` требует единственного server | `s_i` не назван человеческой долей и не нормирован; операция только предшествует processing |
| `H` | analogy | Суммарная требуемая server work, например `sum_i s_i`; при единичных setup — `n` единиц | Это механическая загрузка server, не сумма постановки, чтения, верификации и исправлений разработчика |
| `gamma(P)` | absent | Времена перемещения server между машинами явно равны нулю | Нет context-switch penalty; упомянутая во введении модель Sahney со switching time не является собственной постановкой статьи |
| makespan | direct | `C_max`, основной objective первой части статьи | Нет speedup `T_h/T_ai` и baseline одного разработчика без ИИ |

Дополнительная величина источника `IT` не имеет прямого аналога среди перечисленных параметров. Ближайшая интерпретация — ожидание агентов из-за занятости разработчика, но это не `H` (занятость разработчика), не `gamma(P)` (штраф переключения) и не `C(P)` (agent-agent overhead).

## Что источник поддерживает

1. **Литература scheduling уже содержит модель нескольких параллельных исполнителей и одного общего последовательного ресурса.** Поэтому новизну M4 нельзя формулировать как первое введение общего capacity-1 resource (стр. 2).
2. **Операции общего ресурса должны входить в feasibility расписания, а не только в агрегированную нижнюю границу.** Одновременные запросы к server порождают вынужденный простой машин; порядок setup является частью решения (стр. 2, 9–10).
3. **Makespan и простой из-за общего ресурса — разные objectives.** Статья формально разделяет `C_max` и `IT`, что полезно для разведения итогового времени проекта, человеческой занятости и ожидания агентов (стр. 2, 12–16).
4. **Даже сильно упрощённые single-server variants имеют неоднородную сложность.** Есть псевдополиномиальный двухмашинный случай, unary NP-hardness при произвольном числе машин и специальные полиномиальные случаи для `IT` (стр. 6–8, 8–9, 12–16).
5. **Простые list heuristics требуют явных approximation guarantees.** Для makespan bounds `2 - 1/m` и `3 - 2/m` tight даже при единичных setup times (стр. 9–12).

## Что источник не позволяет утверждать

- Что single server эмпирически или психологически эквивалентен вниманию разработчика.
- Что `s_i` можно без калибровки принять за `h_i Z_i X`, а `sum s_i` — за наблюдаемое человеческое время `H`.
- Что источник подтверждает значения `k_i^(r)`, преимущества ИИ, оптимальное число агентов или ускорение относительно одного разработчика без ИИ.
- Что его алгоритмы и approximation ratios напрямую переносятся на M2–M4: в источнике нет task-precedence DAG, `C(P)`, `gamma(P)`, режима `r`, проверки качества и циклов rework.
- Что forced idle time `IT` является человеческой занятостью. Это время ожидания машин из-за недоступности server.
- Что source учитывает switching cost: напротив, travel times между машинами приняты равными нулю (стр. 2).
- Что Theorem 1 даёт обычный полиномиальный алгоритм: результат псевдополиномиальный (стр. 8).
- Что bounds list scheduling впервые доказаны целиком в этой статье: сами ratios приписаны [2], а здесь доказана их tightness для `s_i=1` (стр. 10–12).
- Что точные номера журнальных страниц отдельных теорем известны по локальному PDF. Проверен только журнальный диапазон 1–11; локальная версия имеет страницы 1–17.

## Отличие от M0–M4

| Измерение | Kravchenko and Werner | M0–M4 |
|---|---|---|
| Исследовательский вопрос | Оптимальное расписание заданных `p_i`, `s_i` на машинах с одним server | Когда один разработчик с `P>1` ИИ-агентами быстрее baseline без ИИ |
| Исполнители | `m` одинаковых машин | Кодовые ИИ-агенты/потоки под контролем одного разработчика |
| Общий ресурс | Механический server выполняет setup перед каждой работой | Разработчик ставит задачи, интерпретирует, проверяет и направляет исправления |
| Время задачи | Отдельные `s_i` и `p_i` | Task/mode-specific `k_i^(r) Z_i X = (a_i^(r)+h_i^(r)) Z_i X` |
| Доступность задач | Все работы готовы в момент 0 | Задачи могут быть связаны DAG; доступность ограничивает критический путь `L` |
| Неделимость | Работы non-preemptive | Уровень M1 вводит неделимые задачи; M0 идеализирует делимость |
| Overhead | Setup и induced idle моделируются операционно | `C(P)` отделяет agent-agent integration overhead; `gamma(P)` — human switching penalty |
| Человеческая доля | Отсутствует | `h_i`, `H` и capacity-1 human intervals заданы явно |
| Objective | `C_max` и отдельно `IT` | Makespan и speedup относительно `T_h`; самостоятельный objective `IT` отсутствует |
| Результаты | Exact/pseudopolynomial algorithms, hardness, tight worst-case bounds | Иерархия нижних границ, критерии ускорения и scheduling feasibility для human intervals |

Наиболее важное отличие состоит в уровне детализации общего ресурса. У Kravchenko and Werner server operation является отдельной фазой каждой работы и включена непосредственно в допустимое расписание. В M4 `H` и `gamma(P)H` дают агрегированное ограничение, а конкретные входные и выходные интервалы разработчика должны дополнительно размещаться в расписании. Поэтому single-server model полезна не как доказательство формулы M4, а как указание на более точный класс расширений: task-specific human operations с capacity 1 и явными временными позициями относительно agent processing.

## Проверенные тезисы для синтеза

1. **Прямой scheduling-прецедент, ограниченная аналогия.** Kravchenko and Werner формализуют `m` одинаковых параллельных машин, обслуживаемых одним server, но server выполняет только детерминированный setup перед processing; интерпретация этого ресурса как человеческого внимания является нашей аналогией, а не результатом источника (стр. 2).
2. **Общий ресурс меняет и сложность, и качество расписания.** `P2,S1 | s_i=1 | C_max` имеет точный псевдополиномиальный алгоритм, тогда как `P,S1 | s_i=1 | C_max` unary NP-hard при произвольном числе машин (Theorems 1–2, стр. 6–9).
3. **Простой ресурса нельзя смешивать с makespan или занятостью server.** Статья отдельно определяет `IT` как вызванное недоступностью server ожидание машин и рассматривает для него собственные algorithms и hardness results (стр. 2, 12–16).
4. **Заявку о новизне M0–M4 следует строить на синтезе, а не на shared-resource primitive.** Отличительный вклад может состоять в совместном учёте task/mode-specific AI duration, DAG/critical path, agent-agent overhead и task-specific human share для software agents; сам primitive «parallel executors + one server» существовал ранее.

## Короткий вариант для Related Work

Kravchenko and Werner (1997) рассматривают детерминированную задачу `P,S1 | s_i | C_max`: `n` non-preemptive работ выполняются на `m` одинаковых параллельных машинах, а setup каждой работы требует единственного общего server. Эта постановка является близким структурным предшественником схемы «несколько агентов — один разработчик», поскольку capacity-1 resource должен быть явно включён в расписание и его занятость может вызывать простой параллельных исполнителей. Авторы дают псевдополиномиальный алгоритм для двух машин и единичных setup times, доказывают unary NP-hardness при произвольном числе машин и анализируют tight worst-case bounds list scheduling; отдельно исследуется forced idle time. Аналогия, однако, ограничена: server выполняет механический setup только до processing, времена перехода равны нулю, а в модели нет task-precedence DAG, режимов взаимодействия, верификации, context switching или task-specific AI effect. Поэтому работа поддерживает shared-resource framing M4, но не идентификацию server с человеческим вниманием и не формулы ускорения M0–M4.

## Итоговая оценка релевантности

Источник высокорелевантен для точного позиционирования **общего последовательного ресурса в parallel-machine scheduling** и для ограничения заявки о новизне M4. Он даёт более близкий формальный аналог, чем общие законы масштабирования: не просто постулирует последовательную долю, а задаёт конкретные server operations, их место перед processing, ресурсную несовместимость и вызванный ею простой. Одновременно источник не является прямой моделью одного разработчика с ИИ-агентами. Корректное использование в Related Work — назвать его структурным предшественником capacity-1 scheduling, затем явно указать, что M0–M4 добавляет software/AI-specific duration factors, режимы, DAG, agent-agent overhead и содержательно человеческие операции постановки и верификации.
