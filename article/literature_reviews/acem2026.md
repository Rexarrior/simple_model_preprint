# El-Ramly: ACEM как непроверенная модель стоимости agentic software engineering

## Назначение и границы обзора

Этот документ разбирает локальный PDF применительно к модели M0--M4 для
fixed-workload makespan ячейки «один разработчик - `P` кодовых ИИ-агентов».
Источник релевантен прежде всего как ранняя попытка формализовать estimation
layer для agentic software engineering: он разделяет token cost, человеческие
review/rework costs и infrastructure cost, вводит поправки на retries и рост
контекста и предлагает локальную калибровку по типам задач.

Главная граница переноса: ACEM оценивает **денежную стоимость и потребление
токенов**, а не elapsed duration или makespan. Работа не содержит фактической
выборки проектов, обученного estimator, holdout validation или variation по
числу параллельных агентов. Более того, её текущая постановка предполагает
последовательный pipeline; parallel multi-agent architectures явно вынесены в
future work. Поэтому ACEM может информировать будущий внешний слой
`\hat{k}_i^{(r)}`, но не даёт готовых `k`, `h`, `C(P)`, `gamma(P)` или результата
о выгоде `P > 1`.

Локальный файл содержит 27 PDF-страниц. Нумерация внизу страниц совпадает с
номерами PDF. Все evidence-ссылки ниже относятся к этой локальной копии.

## Фактический предмет и исследовательский вопрос

### Предмет

ACEM означает **Agentic Cost Estimation Model**. Работа предлагает
параметрическую структуру для оценки полной стоимости agentic software
development как суммы трёх потоков ресурсов (PDF 1, 7--8):

```text
Total_Cost = C_LLM + C_HITL + C_Infra.
```

- `C_LLM` - стоимость input/output tokens всех LLM invocations;
- `C_HITL` - стоимость человеческих review, approval, correction и rework;
- `C_Infra` - compute, sandbox, storage, CI/CD и другие infrastructure costs.

Это не cost model в смысле только developer effort и не scheduling model.
Центральное нововведение автора - перевод artifact size и agentic-process
характеристик в token и HITL cost, а затем в деньги.

### RQ

Нумерованных research questions в PDF нет. Из abstract, introduction и списка
contributions следует один основной проектный вопрос:

> Как связать традиционные software sizing metrics и характеристики agentic
> pipeline с ожидаемыми LLM-token, human-in-the-loop и infrastructure costs,
> учитывая retries, накопление контекста и неодинаковую интенсивность надзора?

Подвопросы структуры модели:

1. Как оценить task-level base input/output tokens по artifact type и
   complexity?
2. Как скорректировать base estimate на rejection/retry cycles через Revision
   Factor и на рост контекста через Context Factor?
3. Как оценить человеческую стоимость review и rework и классифицировать
   oversight через HITL Intensity Score?
4. Как перевести Use Case Points, Story Points и Function Points в base token
   consumption?
5. Как локально откалибровать символические параметры для конкретного
   agent/model/domain и впоследствии проверить predictive accuracy?

Формулировка «предсказывает effort/time» была бы неточной. Duration входит в
ACEM только как review/rework hours, которые умножаются на hourly cost. Главный
outcome - cost, а не wall-clock delivery time (PDF 7--16).

## Данные, sample и tasks

### Фактические данные

**Эмпирической выборки нет.** Работа не сообщает число реальных проектов,
разработчиков, репозиториев, задач или agent runs, на которых ACEM была бы

### Заданная таксономия задач

Вместо observed dataset автор задаёт symbolic `BaseTokens` table из десяти
artifact types и трёх уровней human-perceived complexity (PDF 9--11):

1. requirements elaboration;
2. use case specification;
3. function/method implementation;
4. class/module implementation;
5. unit test suite;
6. integration test scenario;
7. code review;
8. bug diagnosis and fix;
9. documentation;
10. refactoring.

Каждая из 30 ячеек содержит символ `beta`; после калибровки он должен
раскрываться в пару `(beta_in, beta_out)`. Следовательно, полная таблица
фактически требует до 60 скалярных token means, хотя статья называет её
30-constant table. Planning, tool-call formulation и reflection объявлены
agent actions, но отдельные строки для них отсутствуют; автор предлагает
добавить orchestration category или поглотить overhead через Context Factor
(PDF 8, 10--11).

### Иллюстративные задачи

Два worked examples являются гипотетическими, а не наблюдаемыми cases
(PDF 16--19):

- простая client-side validation story, четыре pipeline steps, HIS-2;
- complex multi-file feature, около 25 agent actions, HIS-1.

Все token volumes, rejection rates, retry counts, context coefficients,
review durations и hourly rates в них заданы автором как illustrative
assumptions. Их нельзя использовать как calibration sample или empirical
effect sizes.

## Модель и estimator

### 1. LLM cost

Для `N` agent tasks базовая формула имеет вид (PDF 8--9):

```text
C_LLM = sum_i [(T_in,i + T_out,i) * RF_i * CF_i] * P_model.
```

Далее она расширяется на разные model tiers и разные цены input/output tokens:

```text
C_LLM = sum_j sum_(i in S_j)
        (T_in,i * P_in,j + T_out,i * P_out,j) * RF_i * CF_i.
```

`BaseTokens(type_i, complexity_i)` должен выдавать task-intrinsic input и
output tokens. Carried-forward history намеренно исключается из base input,
чтобы отдельно учитываться через `CF` (PDF 9--11).

### 2. Revision Factor

Revision Factor определён как (PDF 11):

```text
RF_i = 1 + r_i * n_i,
```

где `r_i` - доля rejected outputs данного task type, а `n_i` - среднее число
дополнительных invocations на rejected output. Формула предполагает одинаковую
стоимость исходной попытки и retry; автор прямо считает её conservative lower
bound, поскольку retry обычно несёт дополнительный контекст.

`RF` оценивает ожидаемый token multiplier. Он не является success probability,
duration factor или schedule-dependent rework loop. В частности, временное
положение review и retry в pipeline не моделируется.

### 3. Context Factor

Context Factor задан линейно по позиции задачи в последовательном pipeline
(PDF 11--12):

```text
CF_i = 1 + alpha * (i / N).
```

Он переводит task-intrinsic input estimate в position-aware forecast. Если
из API logs уже взято полное context-inclusive input-token count, повторно
применять `CF` нельзя. При context reset автор предлагает возвращать `CF` к
`1.0`.

Линейная позиция `i/N` - упрощённый proxy: она не измеряет фактический размер
контекста, не учитывает неодинаковые contributions задач и не описывает DAG или
parallel branches. Формула `C_LLM` умножает на `CF` и input, и output terms,
хотя содержательное объяснение `CF` относится прежде всего к росту input
context; отдельная эмпирическая проверка такого общего multiplier отсутствует.

### 4. HITL cost и oversight

Человеческий компонент (PDF 12--13):

```text
C_HITL   = C_review + C_rework
C_review = sum_i K_i * D_i * W
C_rework = sum_i r_i * RW_i * W.
```

- `K_i` - число review checkpoints;
- `D_i` - средняя длительность checkpoint в часах;
- `RW_i` - human rework duration при rejection;
- `W` - fully loaded hourly reviewer cost.

HITL Intensity Score задаёт четыре ordinal levels:

| Уровень | Смысл | Typical checkpoints |
|---|---|---|
| HIS-1 Minimal | review на milestone boundary | один на epic/feature |
| HIS-2 Standard | review на story/use-case level | один на story/use case |
| HIS-3 Elevated | review каждой задачи | один на task |
| HIS-4 Continuous | approval каждого agent action | каждый action |

HIS выбирается по domain risk, agent reliability, task complexity и
regulatory requirements. Это planning classification, не оценённая шкала:
межэкспертная надёжность, predictive validity и связь HIS с фактическими
`K_i`, `D_i` не проверены (PDF 12--13).

Planning и architecture названы частью изменившейся человеческой роли, но
текущая формула HITL отдельно учитывает только review и rework; этот пробел
прямо признан в Section 3.3 (PDF 12).

### 5. Sizing mappings

ACEM предлагает три project-scope proxy (PDF 14--16):

```text
T_base,total = U_UCP * gamma_UCP
T_base,total = SP_s * gamma_SP * CW_s
T_base,total = FP * gamma_FP.
```

Затем project-level estimate использует average factors:

```text
C_LLM = T_base,total * RF_avg * CF_avg * P_model.
```

Используются unadjusted UCP и FP, поскольку classical adjustment factors
описывают human implementation environment и могут не соответствовать
LLM-perceived complexity. Для Story Points `CW_s` нормируется относительно
medium-complexity stories.

Это заявленные функциональные формы, а не установленные зависимости. В
Story-Point equation правая часть относится к story `s`, но слева обозначен
project total; явная сумма по stories в формуле не записана. Ни один `gamma`
не оценён, linear proportionality не проверена, predictive intervals не даны.

## Input features и calibration

### Требуемые признаки

ACEM предполагает следующие группы inputs:

- artifact type и human-perceived complexity;
- marginal task input, total context-inclusive input и output tokens;
- agent implementation, model/version, prompt design и domain;
- task position в pipeline и context-reset policy;
- rejection indicator и число retry invocations;
- UCP, SP или FP и complexity weight;
- число review checkpoints, review duration, rework duration и reviewer rate;
- domain risk, agent reliability и regulatory requirements для HIS;
- unit prices LLM и infrastructure resources.

Language/encoding, formatting, model verbosity, retrieval, deep reasoning и
prompt caching обсуждаются как возможные drivers LLM-perceived complexity, но
в итоговой базовой спецификации не образуют отдельный fitted feature vector
(PDF 9--10).

### Предлагаемая calibration procedure

Автор задаёт четыре шага (PDF 16):

1. Выполнить representative pilot, рекомендуя минимум три задачи на каждую
   используемую artifact-type/complexity cell. Отдельно записывать marginal
   task input и полный context-inclusive input.
2. Для каждой ячейки вычислить средние input/output tokens и standard
   deviation.
3. Оценить rejection rate `r_i`, mean retries `n_i` и fit `alpha` регрессией
   token consumption на task position с контролем artifact type и complexity.
4. Получить `gamma_UCP`, `gamma_SP` или `gamma_FP` делением observed base tokens
   на sizing metric; для SP отдельно оценить `CW` относительно medium tasks.

Полная схема требует 30 task/complexity cells; при заявленном минимуме это не
менее 90 pilot tasks. Для малого корпуса предлагается reduced scheme с 5--8
aggregated constants. Утверждение, что три наблюдения на ячейку дают stable
estimate, не сопровождается power, precision или interval calculation.

Константы объявлены agent-, model-, prompt-, domain- и version-specific.
Рекомендуются calibration log и повторная калибровка при смене tooling или
domain. Это согласуется с context-specific `\hat{k}`, но частота обновления и
drift threshold не установлены (PDF 10--11, 16, 19, 22--23).

## Validation design

### Что выполнено

Фактическая validation отсутствует. Worked examples проверяют только
арифметическое прохождение через формулы и не сравнивают прогнозы с observed
costs (PDF 16--19).

### Что запланировано

Future-work program включает (PDF 21--24):

1. multi-organization data не менее чем для трёх agents/models и application
   domains;
2. calibration на pilot subset и held-out evaluation;
3. отдельную точность `C_LLM`, `C_HITL` и total cost;
4. метрики MMRE, PRED(25) и MdMRE;
5. baselines: raw UCP/SP extrapolation, Hybrid Intelligence Effort и simple
   linear/regression token estimators без RF/CF/HIS;
6. sensitivity analysis RF, CF и HIS;
7. cross-agent/model transfer;
8. practitioner usability study;
9. longitudinal, online и domain-specific recalibration.

Это protocol proposal, не выполненный study design. Не заданы sample sizes,
sampling frame, preregistration, split proportions, loss function для fitting,
handling clustered tasks/projects, missing data, leakage controls или критерий
успешной validation.

## Findings, exact results и uncertainty

### Собственные empirical findings

Их нет. Все `beta`, `gamma`, `alpha`, RF/CF values и HIS-to-duration relations
не оценены. Следовательно, ACEM не сообщает predictive accuracy, effect size,
uncertainty interval или evidence, что её структурные поправки превосходят
простую regression.

Утверждения related-work section о 55% ускорении Copilot, `30x` token
variation, Story Points/HIE и других внешних результатах являются пересказом
цитируемых источников, а не собственными данными ACEM. Для использования этих
чисел как evidence нужны соответствующие первичные работы.

### Иллюстративный пример 1

Для simple four-step pipeline автор задаёт 68,000 input и 16,000 output base
tokens, `r=0.15`, `n=1.5`, `RF≈1.22`, `alpha=0.08`, `CF≈1.05`, one review
checkpoint, review `0.167 h`, rework `0.333 h`, reviewer `$30/h`. Таблица
сообщает `C_LLM≈$0.38`, `C_HITL≈$6.51`, total `$6.93` и долю LLM `≈5.5%`
(PDF 17).

В таблице есть арифметическая несогласованность: `$0.38 + $6.51 = $6.89`, а
не `$6.93`. При неокруглённых `RF=1.225` и `CF=1.05` token cost остаётся около
`$0.381`, так что total также около `$6.89`. Разница мала для демонстрации, но
подтверждает, что числа нельзя трактовать как validated result.

### Иллюстративный пример 2

Для complex feature автор задаёт 3,000,000 input и 800,000 output base tokens,
`r=0.45`, `n=1.8`, `RF≈1.81`, blended `CF≈1.4`, one review hour, expected human
rework `0.45*3 h` и reviewer `$50/h`. Получаются `C_LLM≈$35.48`,
`C_HITL≈$117.50`, total `≈$152.98`, LLM share of total `≈23.2%` (PDF 18--19).

`CF=1.4` здесь не является прямым средним Equation 7: сноска на PDF 19
называет его blended approximation, weighted toward late steps. Base token
counts и все остальные inputs также assumed.

Discussion говорит, что “`C_LLM`'s share of `C_HITL`” растёт с 5.5% до 23.2%,
но таблицы делят `C_LLM` на **Total Cost**. Для второго примера отношение
`C_LLM/C_HITL` равно примерно 30.2%, не 23.2%. Безопасно цитировать только
«illustrative share of stated total cost», а не эмпирическую долю или долю от
HITL.

### Uncertainty

В calibration plan предлагается хранить mean и standard deviation `beta`, а
discussion признаёт, что agentic cost лучше описывать распределением и что
Monte Carlo или Bayesian estimation могут быть уместнее point estimate
(PDF 16, 20). Однако ACEM в текущем виде детерминирована:

- не задаёт распределений token/retry/HITL variables;
- не выводит variance total cost;
- не учитывает covariance BaseTokens, RF и CF;
- не строит confidence или prediction intervals;
- не задаёт quantile/risk objective.

Автор отдельно признаёт identifiability risk: aggregate totals не позволяют
разделить retries и context growth, а complexity может одновременно влиять на
BaseTokens, RF и CW, нарушая construct separability (PDF 16, 19).

## Что именно предсказывает ACEM

| Outcome | Статус в ACEM | Граница |
|---|---|---|
| Input/output token consumption | Центральный прогнозируемый intermediate outcome | Пока только symbolic, без fitted constants |
| LLM monetary cost | Центральный outcome | Зависит от token forecast и текущих prices |
| Human review/rework effort | Вводится через hours `K_i D_i` и `r_i RW_i` | Planning/architecture не выделены; overlap и schedule не моделируются |
| HITL monetary cost | Центральный outcome | Human hours умножаются на hourly rate `W` |
| Infrastructure cost | Добавочный outcome | Обычная unit-cost сумма, без новой calibration model |
| Total monetary cost | Главный итог | Additive pragmatic approximation |
| Elapsed task duration | Не предсказывается | Token count и human effort не преобразуются в wall-clock service time |
| Project makespan | Не предсказывается | Нет allocation, DAG, critical path и resource-feasible schedule |
| Quality | Не предсказывается | Используется только косвенно через rejection/reliability assumptions |
| Success probability | Не предсказывается | Rejection rate является input; benchmark success может дать грубую инициализацию RF |

Таким образом, ACEM не следует помещать в одну строку с duration-effect studies
как ещё одну оценку `k`. Это proposal cost estimator с неоценёнными
параметрами.

## Связь с внешним `k_hat`

В M0--M4

```text
k_i^(r) = T_i^ai(r) / (Z_i X)
```

требует прогноза полного one-stream elapsed time при доступном разработчике,
включая specification, generation, verification и correction. ACEM такой
`T_i^ai(r)` не выдаёт.

Полезная связь ограничена тремя уровнями:

1. **Feature schema.** Artifact type, complexity, context growth, rejection,
   retries, oversight intensity и model/version могут стать predictors
   `\hat{k}_i^(r)`.
2. **Telemetry protocol.** Разделение marginal input, carried context,
   rejection events, retries, review и rework помогает избежать двойного
   учёта и собирать task-level calibration data.
3. **Cold-start warning.** Константы должны быть local и version-specific;
   illustrative benchmark values не заменяют prospective validation.

Но ACEM cost нельзя механически преобразовать в `\hat{k}`:

- dollar cost не равен времени;
- token count не задаёт agent elapsed latency без модели throughput/tool calls;
- сумма human hours не показывает, где они расположены и перекрываются ли с
  agent work;
- no-AI denominator `Z_i X` не моделируется;
- project sizing proxy не является paired no-AI baseline;
- sequential cost aggregation не строит schedule при `P > 1`.

Практически ACEM можно использовать как источник candidate features для
отдельного duration estimator. Его predictive validity для `\hat{k}` должна
проверяться заново на outcome M0--M4, а не наследоваться из cost formulas.

## Полное mapping к M0--M4

Обозначения двух работ частично конфликтуют. Особенно важно не смешивать
`r_i`, `W` и `P`: в ACEM это rejection rate, hourly wage и token price, а не
режим, aggregate work и число агентов.

| Параметр M0--M4 | Статус | Ближайший объект ACEM | Точная граница |
|---|---|---|---|
| `X` | **absent** | Traditional sizing metrics задают project scope | Нет общей baseline duration единицы без ИИ |
| `Z_i` / `Z` | **analogy** | UCP/SP/FP, artifact type и Simple/Medium/Complex | Это sizing/complexity proxies для tokens, не `Z_i X` no-AI time |
| `k_i^(r)` / `k` | **absent; feature support** | BaseTokens, RF, CF и HITL hours могут объяснять AI workload | Нет ratio AI elapsed duration к no-AI baseline |
| режим `r` M0--M4 | **analogy** | HIS-1--HIS-4, autonomy и task/model/domain context | ACEM `r_i` означает rejection rate, не interaction mode; режим не задаётся как task assignment `rho(i)` |
| `P` M0--M4 | **absent** | `P_model`, `P_j`, `P_in,j`, `P_out,j` - цены токенов | Ни один `P` ACEM не является числом concurrent agents; parallelism не варьируется |
| `N` | **partial direct count** | Число agent tasks | Гранулярность task/action неоднозначна; planning actions не полностью покрыты BaseTokens table |
| `W = X sum Z_i k_i` | **absent** | Token totals и total cost агрегируются по задачам | ACEM `W` - reviewer hourly cost; его нельзя подставлять как aggregate workload |
| неделимость / `M_N` | **absent** | Artifact/task является единицей подсчёта | Нет nonpreemptive allocation и longest-job bound |
| DAG / `L` | **absent** | Последовательная позиция `i/N` в CF | Нет precedence graph, critical path или path weights |
| `C(P)` | **absent** | RF и CF повышают token consumption | Это one-pipeline retry/context factors, не overhead от роста числа parallel agents |
| `h_i` / `h` | **analogy, не нормировано** | `K_i D_i + r_i RW_i` задаёт expected human review/rework hours | Нет деления на `Z_i X`, полного specification/planning time и двухканального wall-clock split |
| `H` | **analogy, не scheduling resource** | Сумма review/rework hours до умножения на wage | Не доказано, что интервалы принадлежат одному capacity-1 developer; их временное положение не задано |
| `gamma(P)` | **absent** | Context Factor относится к LLM context | Нет human context-switch penalty между concurrent streams и зависимости от agent count |
| makespan | **absent** | Total cost | Нет completion-time objective, feasible schedule или speedup baseline |

### Ближайшие структурные соответствия

- ACEM `BaseTokens(type, complexity)` ближе всего к estimator features для
  task-specific `\hat{k}`, но его target другой.
- ACEM `RF` описывает retry workload, который при duration measurement должен
  уже входить в `k_i^(r)` для `P=1`; это не отдельный M3 multiplier.
- ACEM `CF` описывает context growth внутри длинного pipeline. В M0--M4 такой
  one-stream effect также должен входить в mode-specific `k`, если он уже
  наблюдался при `P=1`. Только дополнительный рост из-за concurrent streams
  может относиться к `C(P)` или `gamma(P)` после отдельной идентификации.
- HITL formula подтверждает необходимость отдельно измерять review/rework,
  но M4 требует ещё временного размещения human intervals и capacity-1
  feasibility.

## Что источник поддерживает

1. Agentic software engineering требует учитывать не только traditional
   developer effort, но и token, human review/rework и infrastructure costs
   как разные resource streams (PDF 1--3, 7--8).
2. Task type, complexity, model/version, prompt design и domain должны входить
   в context-specific calibration; универсальные constants автор не заявляет
   (PDF 9--11, 16, 19).
3. Rejections и retries создают одновременно дополнительный agent workload и
   дополнительную human correction work; эти потоки нельзя считать одной и
   той же monetary cost (PDF 7--8, 11--12).
4. Context-inclusive input logs нельзя повторно умножать на Context Factor:
   source прямо предупреждает о double counting (PDF 11, 16).
5. Review checkpoint count, duration, rejection и rework duration являются
   полезными наблюдаемыми признаками human involvement (PDF 12--13).
6. Traditional sizing metrics можно рассматривать как candidate scope proxies,
   но их связь с token consumption должна быть установлена локальной
   калибровкой, а не объявлена conceptual equivalence (PDF 14--16).
7. Нужны version-specific calibration logs, held-out evaluation, sensitivity
   analysis и comparison с simpler baselines (PDF 16, 21--24).
8. Deterministic point estimate недостаточен при stochastic agent behavior;
   probabilistic cost distribution обозначена автором как необходимое future
   extension (PDF 20).
9. Parallel multi-agent pipeline не покрыт текущей ACEM и является future work
   (PDF 19).

## Что источник не позволяет утверждать

1. Что ACEM опубликована, прошла peer review или зарегистрирована на arXiv.
2. Что библиографический год равен 2026 только потому, что так назван файл.
3. Что `beta`, `gamma`, `alpha`, RF, CF или HIS empirically calibrated.
4. Что ACEM показывает predictive accuracy лучше UCP, Story Points, HIE или
   simple regression: comparison только запланирован.
5. Что три pilot tasks на cell действительно обеспечивают stable estimates.
6. Что Story Points, UCP или FP линейно предсказывают token consumption: это
   hypothesis embodied in formulas, не finding.
7. Что worked-example costs являются наблюдаемыми industry averages или
   confidence bounds.
8. Что LLM cost обычно составляет 5.5% или 23.2% total cost: эти доли получены
   из assumed examples и одна таблица содержит arithmetic inconsistency.
9. Что ACEM прогнозирует developer productivity, elapsed task duration,
   project schedule или makespan.
10. Что снижение token cost сокращает delivery time: price, tokens, latency и
    human waiting являются разными outcomes.
11. Что rejection rate ACEM равен режиму `r` M0--M4 или что hourly `W` ACEM
    равен aggregate work `W` M0--M4.
12. Что `P_model` обозначает parallelism; это цена токена.
13. Что RF или CF являются `C(P)`: они не зависят от числа concurrent agents.
14. Что HITL cost задаёт `h` или `H` без нормировки, полного human-action scope
    и resource-feasible timing.
15. Что HIS является validated psychometric или operational scale.
16. Что модель учитывает planning/architecture effort полностью: текущая HITL
    formula отдельно считает review и rework.
17. Что additive monetary components независимы в causal/statistical смысле:
    автор называет additivity pragmatic simplification и признаёт interactions
    (PDF 7--8, 19).
18. Что current ACEM применима к parallel multi-agent architectures, DAG,
    critical path, agent allocation или context switching человека.
19. Что external empirical claims в related work становятся собственными
    findings ACEM.

## Отличие от M0--M4

| Измерение | ACEM | M0--M4 |
|---|---|---|
| Центральный вопрос | Как оценить monetary cost agentic software project | Когда `P>1` сокращает fixed-workload makespan и что ограничивает speedup |
| Статус | Symbolic early-stage proposal без validation | Детерминированная formal scheduling/scalability model с внешней calibration need |
| Outcome | Tokens, HITL cost, infrastructure cost, total cost | Elapsed makespan и speedup относительно no-AI baseline |
| Baseline | UCP/SP/FP или BaseTokens | `T_h=X sum Z_i` одного разработчика без ИИ |
| Task heterogeneity | Artifact type, three complexity levels, task-specific RF | `Z_i`, task/tool/mode-specific `k_i^(r)` и `h_i^(r)` |
| Human work | Review checkpoints и expected rework hours, затем wage | Human intervals `h_i`, capacity-1 sum `H`, switching `gamma(P)` |
| Agent process | Sequential actions/tasks с retries и growing context | До `P` parallel agent streams, indivisibility и allocation |
| Dependencies | Sequential position only | DAG и critical path `L` |
| Parallel overhead | Не моделируется; parallel architectures future work | Agent integration `C(P)` и human switching `gamma(P)` |
| Uncertainty | Mean/SD proposal; probabilistic model future work | `k` допускается как random input, deterministic core and bounds |
| Validation | Planned pilot, holdout and baselines | Требуется внешняя empirical calibration of durations and human shares |

ACEM расположена рядом с **estimation layer**, но с другим target. Она пытается
оценить ресурсную и денежную нагрузку будущего agentic project. M0--M4 принимает
или оценивает task durations и затем решает вопрос fixed-workload completion
time при ограниченном параллелизме, зависимостях и одном human resource.
Модели потенциально дополняют друг друга, но ни одна не является частным
случаем другой без дополнительного преобразования tokens/costs в фазовые
durations.

## Claims для Related Work

### Безопасные claims

1. El-Ramly предлагает ACEM как невалидированную параметрическую модель
   agentic-development cost, складывающую LLM-token, HITL и infrastructure
   components; параметры оставлены symbolic (PDF 1, 7--16, 24).
2. ACEM разделяет task-intrinsic BaseTokens, retry multiplier RF и
   position-based Context Factor и требует калибровать их для конкретного
   agent/model/domain (PDF 9--12, 16).
3. HITL component считает review checkpoints и expected human rework, а HIS
   классифицирует oversight от milestone review до approval каждого action
   (PDF 12--13).
4. UCP, Story Points и Function Points предложены как calibration-based proxies
   token consumption, но связь пока не проверена на данных (PDF 14--16).
5. Работа не оценивает elapsed duration и предполагает sequential pipeline;
   parallel multi-agent architectures и predictive validation оставлены
   future work (PDF 19, 21--24).

### Claims, которых следует избегать

- «ACEM доказала, что Story Points предсказывают agent token cost».
- «ACEM валидирована на real-world projects».
- «ACEM оценивает оптимальное число агентов».
- «RF и CF объясняют makespan или diminishing returns по `P`».
- «HIS измеряет человеческую долю `h`».
- «ACEM даёт `k_hat` для M0--M4».
- «В agentic development LLM cost составляет 5.5--23.2% total cost».
- «Источник является peer-reviewed preprint 2026 года» без внешней записи.

## Короткий вариант встраивания

> El-Ramly предлагает ACEM, раннюю невалидированную структуру оценки стоимости
> agentic software engineering. Модель складывает LLM-token, human-in-the-loop
> review/rework и infrastructure costs, отделяет task-intrinsic BaseTokens от
> retry multiplier и линейной поправки на накопление контекста и предлагает
> локально калибровать эти параметры по artifact type, complexity,
> agent/model/domain и традиционным sizing metrics. Для нашей работы ACEM
> полезна как набор candidate features и telemetry requirements внешнего
> estimation layer: rejection, retries, context-inclusive tokens, review и
> rework действительно следует измерять раздельно. Однако константы ACEM
> оставлены символическими, real-project validation отсутствует, а target
> модели - monetary cost, не elapsed duration. Текущая ACEM предполагает
> последовательный pipeline и не моделирует число concurrent agents, DAG,
> critical path, resource-feasible human intervals или makespan; поэтому она
> не даёт `\hat{k}_i^{(r)}` и не заменяет уровни M0--M4.

## Итоговая оценка релевантности

Источник релевантен M0--M4 как соседняя современная попытка построить
AI-specific estimation framework и как конкретный список telemetry fields:
task type, complexity, token channels, context position, rejection, retries,
review и rework. Особенно полезны предупреждения о version-specific calibration,
double counting context и неидентифицируемости RF/CF по aggregate totals.

Доказательная сила источника пока ограничена formal proposal. У него нет
dataset, fitted coefficients, uncertainty estimates или validation results;
работа не предсказывает duration, success или quality и не рассматривает
parallel scheduling. Корректное место в Related Work - после классического
software effort/cost estimation как emerging agentic-cost proposal, с явным
контрастом: ACEM оценивает cost streams, тогда как M0--M4 оценивает
fixed-workload makespan и требует отдельного внешнего duration estimator.
